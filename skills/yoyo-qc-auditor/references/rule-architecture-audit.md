## 二、为什么用 DB 而不是快照

盘查过程中发现一个会让所有结论失真的坑：

> `~/.workbuddy/automation-backups/*.json` **不随 `automation_update` 刷新**，
> 2026-09-14 实测滞后 **8–12 天**。

第一版门禁就是拿它跑的，差点得出「复制率仅 7%」的假结论。
**正解**：`workbuddy.db` 的 `automations` 表有 `prompt` + `updated_at` 字段，是唯一 live 真相源。

```bash
sqlite3 ~/.workbuddy/workbuddy.db \
  "SELECT id,name,length(prompt),updated_at FROM automations ORDER BY updated_at DESC"
```

因此门禁新增 `--db` 模式直读库；人工快照（`.rule-ref/`）降级为 DB 不可用时的备选，
并保留 D 项专门检测「快照陈旧导致的假绿灯」。

## 九、方法论沉淀：三类判据的边界

盘查中踩了 3 个误报坑，全部已修——**有误报的门禁会被弃用，比漏报更糟**：

| 误报源 | 症状 | 修正 |
|---|---|---|
| 数量下限正则过宽 | `>=1.0.69`（版本号）、`count>0`、`exit code=2`（脚本状态）被当成规则 | 要求**后接量词**（`≥8 条` ✓） |
| 比例正则过宽 | `23:59:59` / `00:00:00`（时间戳）命中 `N:M:N` | 限定**各项为单个数字** |
| 表格一律算规则 | 自动化自身的步骤表（QC 三层检查项）被误判 | 表格**只作 E2 证据**，不单独触发 E1 |

**另一条边界**：`skills_json` 为空属机制现状，不是缺陷 → 必须降为提示，
否则门禁会长期挂着 11 条假警告，最终被忽略。

## 十、与「三角色模型」的关系

本次盘查是 `references/rule-ref-discipline.md` 的**落地验证**：

| 角色 | 该写 | 本次发现问题 |
|---|---|---|
| SKILL.md | 规则唯一真相源 | **1.5% 有版本戳** → 真相源无法版本化 |
| 自动化 prompt | 只写执行契约 + 引用 | 3 条仍有副本（已修）、2 条规则孤本、7 条资产指向易失目录 |
| memory | 教训 + 指针 | 无问题 |

判据始终是一句：**「我要改这个值，需要动几个文件？」答案 >1 就是设计错了。**
