# 规则引用纪律：从「三处一致」到「一处定义 + 两处引用」

> 适用：任何「skill 规则 + 自动化 prompt + memory」同时描述同一件事的场景。
> 配套门禁：`scripts/rule_ref_lint.py`。首次落地案例见 `overseas-news-daily`（2026-09-14）。

---

## 一、被纠正的那条规则

> ❌ 旧规则：「规则改动要 **SKILL.md / 自动化 prompt / memory.md 三处一致**」

**这条规则本身是病。** 它把「保持 N 份副本同步」当成纪律，等于先承认有 N 份副本。
副本数 ≥ 2 时，漏一处只是时间问题——不是态度问题，是结构问题。

**判据（很土但准）**：

> **「我要改这个值，需要动几个文件？」答案 > 1 就是设计错了。**

正确的做法不是「记得同步另外两处」，而是**消灭另外两处**。

---

## 二、正解：三处不是三份副本，是三个角色

三者的**职责必须互斥**，通过**单向引用**串联，而不是互相抄。

| 层 | 角色 | 该写什么 | 禁止写什么 |
|---|---|---|---|
| **SKILL.md**（含 `references/`） | **规则唯一真相源** | 阈值 / 判据 / 清单 / 比例 / 正则 / 流程；版本戳 `RULE_VERSION`；变更日志 | 会变的具体数据（客户事实 → `client-facts.md`）；变更史之外的运营细节 |
| **自动化 prompt** | **执行契约（触发器 + 绑定）** | 触发时机；`sed` 读哪几节；工作目录 / 表ID / 脚本入口 / 会话ID；交付物；报告回执格式 | **任何规则内容**——阈值、清单、比例、判据、正则 |
| **memory** | **教训 + 指针** | 为什么这么设计、踩过什么坑、去哪找真相 | **任何会变的数或规则内容** |

> 三者「一致」是错误目标。正确目标是：**规则只在 SKILL.md 出现一次，另外两处只出现「指针」**。

### 一个判断口诀
- prompt 里出现「≥8 条 / 1:2:1 / 禁 8 类 / 30 天」→ **抄了规则，要改**
- prompt 里出现「见 §9d」→ **对了**
- memory 里出现「当前阈值是 8」→ **抄了数据，要改成指针**

---

## 三、prompt 的标准四段结构

```markdown
## 任务：<一句话>

> 规则版本：YYYY.MM.DD ｜ 执行前核对 SKILL.md 头部 RULE_VERSION；
> 不一致 → 先读文末「规则变更日志」再执行，并在报告标注「规则版本跳变」。
> 本 prompt 只写「读哪一节」与「执行契约」，不复刻规则内容。

### 📖 规则读取（唯一真相源；禁止全量 Read）
```bash
S=<SKILL.md 绝对路径>
sed -n '/^### 9d\./,/^### 10\./p' $S   # §9d 分类比例（正则区间：行号变了也不会错）
```
> 上述区间的所有判据、阈值、清单一律照 SKILL.md 执行，本 prompt 不再复述。

### 执行契约（本自动化独有，非规则）
- 表 ID / 脚本路径 / 工作目录 / 会话 ID / 交付物格式

### 执行步骤
Phase/步骤（描述「做什么 + 读哪节」，不写判据）

### 📋 报告回执（必做）
规则版本 / 关键计数 / 异常与未解决（含「读到区间为空」）
```

> 用 **`sed` 正则区间**而不是行号，是为了让 SKILL.md 增删行时不失效。
> 但**章节标题本身**仍是硬依赖——改名即失效，这正是门禁 A 项要抓的。

## 四、七项判据与门禁对应

> **数据源（2026-09-14 起）**：`--scan` **直读** `~/.workbuddy/workbuddy.db` 的
> `automations.prompt` 字段——这是唯一 live 真相源。人工快照（`.rule-ref/`）
> 降级为 DB 不可用时的**备选**，并由 D 项专门检测其陈旧。

```bash
S=~/.workbuddy/skills/yoyo-qc-auditor/scripts/rule_ref_lint.py
python $S --scan                                # 全量盘查（架构级，含 skill 侧体检）
python $S --skill <SKILL.md> --db --ids <id>    # 单链路深查
python $S --scan --json                         # 纯 JSON（供自动化消费）
```

| 项 | 失效模式 | 后果 | 判定 |
|:-:|---|---|---|
| **A** | **锚点失效**：prompt 里 `sed -n '/^### 9d/…'`，SKILL.md 已改名 | **静默返回空 → 自动化盲跑（最凶）** | **FAIL** |
| **B** | **版本漂移**：SKILL.md 升版，prompt 仍声明旧版 | 按旧规则执行，结果看似正常 | 不一致 = **FAIL**；未声明 = WARN |
| **C** | **规则复制**：prompt 复刻了阈值/清单 | 改了 SKILL.md，prompt 那份没改，两份打架 | 公共文本占比 > 12% = WARN |
| **D** | **快照陈旧**：拿旧 prompt 跑门禁 | **假绿灯** | 快照比 SKILL.md 旧 = WARN（`--db` 下不适用） |
| **E1** | **规则双份**：有 skill 引用，却仍在 prompt 内联规则 | skill 改了不生效，执行旧版且无人知 | WARN |
| **E2** | **规则孤本**：规则只活在 prompt，无 skill 承载 | 无法版本化、无法回归、无法审计 | WARN |
| **F** | **依赖未声明**：prompt 引用 skill 但 `skills_json` 空 | 无法静态校验绑定关系（不影响执行） | P2 提示 |
| **G** | **易失资产**：脚本存于 `/WorkBuddy/<时间戳>/` 会话目录 | 清理旧工作区即全链失联 | WARN |

> **A 是最高优先级**：B/C 至少还能从内容看出来，A 是「规则根本读不到」——脚本不报错、
> 流程照跑、结果照出，只有规则全丢。这就是典型的需要门禁才能发现的静默失败。

### 判据的边界（防误报 —— 有误报就会被弃用，比漏报更糟）

E1/E2 依赖「**规则指纹**」——只认规则才会长成的形状（`N:M:N` 比例、带量词的数量上下限、
`N 天内` 时间窗口、`第N优先`、`八类`、黑白名单、编号规则、数据质量铁律、≥4 行内联清单表）。

建门禁时踩过 3 个误报坑，全部已修：

| 误报源 | 症状 | 修正 |
|---|---|---|
| 数量下限正则过宽 | `>=1.0.69`（版本号）、`count>0`、`exit code=2` 被当成规则 | 要求**后接量词**（`≥8 条` ✓） |
| 比例正则过宽 | `23:59:59` / `00:00:00`（时间戳）命中 `N:M:N` | 限定**各项为单个数字** |
| 表格一律算规则 | 自动化自身的步骤表（如 QC 三层检查项）被误判 | 表格**只作 E2 证据**，不单独触发 E1 |

**另一条边界**：`skills_json` 为空是当前平台机制现状（该字段未启用），**不是用户缺陷** →
必须降为提示，否则门禁会长期挂着 11 条假警告，最终被忽略。

## 五、迁移步骤（把一个「三处一致」的体系改对）

1. **建版本戳**：SKILL.md 头部加 `<!-- RULE_VERSION: YYYY.MM.DD -->` + 文末「规则变更日志」表。
2. **盘点副本**：逐条列出 prompt/memory 里复刻的规则项，对照 SKILL.md 确认**是否已存在**。
   - 已存在 → 删副本，改引用
   - **不存在 → 先搬进 SKILL.md，再删副本**（顺序反了会丢规则）
3. **改写 prompt** 为四段结构；每处引用用 `sed` 正则区间。
4. **跑门禁** `rule_ref_lint.py --scan`：A 必须 0 FAIL；B 一致；E1/E2 归零；C 低于阈值。
5. **登记变更日志**，并把「prompt 只引用不复刻」写进 SKILL.md 开头。

> **顺序铁律**：先改**源头**（SKILL.md），再改**引用方**（prompt）。反过来必丢规则。
> **陷阱**：「改造半截」比不改造更危险——prompt 里留着旧副本，skill 改了不生效，
> 执行的是 prompt 旧版且无人知。**改完必须跑门禁复核，不能凭印象说改完了。**

## 六、遗留边界（诚实说明）

- **已解决**：门禁不再依赖人工快照新鲜度——`--db` / `--scan` 直读 `workbuddy.db`，
  可自动拿到 live prompt。D 项仅在降级用快照时才适用。
- C 项是启发式（公共文本占比），会有假阳性/假阴性，定位为**提示**而非硬失败。
- E1/E2 依赖规则指纹，**只能发现「像规则的东西」**；纯自然语言表述的规则可能漏过。
  真实兜底仍是人工 review。
- 该纪律要求 prompt 能执行 `sed`/读文件；纯自然语言的第三方自动化无法纳入。
- 全量盘查结论见 `rule-architecture-audit.md`（11 条自动化 / 65 个 skill 的实测）。
