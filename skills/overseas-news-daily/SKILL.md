每条写入的记录必须判断是否精选。每日推送优先从「精选」记录中选择。

**非精选（false）条件（满足任意一条）：**

**默认值：** 未明确判断时默认为非精选（false）。

### 60天内同题去重规则

写入前必须检测是否与**过去60天内已有记录**属于同一主题。同一主题在60天内只应出现一次。

**去重判定标准（命中任意一条即视为同主题）：**
1. 标题提及同一法规/政策名称（如"837号令""新加坡LQS""欧盟AI法案""沙特Nitaqat"）
2. 标题提及同一国家+同一事件类型（如"墨西哥工时改革""印尼镍矿配额""越南最低工资"）
3. 标题提及同一家具体企业的同类事件（如"比亚迪海外建厂""宁德时代投资"）

**去重执行逻辑：**
1. 查询表中所有（含已推送）标题，提取关键词匹配
2. 如果新采集内容与已有记录为同一主题：
   - **已有记录信息更新**（如欧盟AI法案延期）：用新内容覆盖旧记录，保留旧记录的推送状态
   - **已有记录信息未变化**（如同日重复采集）：跳过不写入
3. 60天内的排序优先：较新的版本保留，较旧的删除

**判定规则：** 来源字段含竞品名称（子串匹配）或原文链接域名匹配竞品域名，**即使正文内容有价值也一律跳过**。

### 溯源增强规则（2026-07-10 新增）

当采集到的信息来源为**出海人力资源服务公司**（EOR/Payroll/名义雇主/HR咨询等）时：

1. **判断来源性质** — 来源字段或原文链接是否指向HR服务商官网/白皮书/博客
2. **溯源查找** — 如果该信息引用的是某个具体的政策/法规/事件，找到该政策的原发官方来源（政府公告、国际组织、权威媒体）
3. **替换来源引用** — 在正文的【来源引用】中以官方/权威来源为准，而不是HR服务商
4. **无法溯源则不采集** — 如果找不到原始政策来源（是HR服务商基于公开信息的二次整合），则跳过不采集

### 6. 内容撰写规范

#### 标题
- 按事件类型自然表达，15-25字

#### 正文结构（统一模板）

```
【事件概述】
（充分展开政策/事件的核心内容、生效时间、适用范围、涉及主体）

【背景分析】
（政策出台的背景、历史对比、市场特殊性、相关政策联动）

【关键数据】
（提炼具体数据：金额、比例、时间节点、量化影响）

【影响解读】
（从中国出海企业HR视角分析实际影响与应对建议）

【来源引用】
```

正文不限字数，以"足够完整传达核心信息"为准。

#### Q&A 节（每篇3-5条，基于 AEO 方法论）

每条正文后必须追加 Q&A 节，从正文中提取 3-5 条用户会在 AI 中搜索的真实问题。

**设计原则（基于 AEO 方法论）：**
1. **基于正文，不编造** — 每条 Q&A 的答案必须能在正文中找到依据，不可凭空想象
2. **模拟用户提问** — 每个问题控制在 15-25 个字，像出海HR从业者真实会问的
3. **覆盖常用问题类型**：是什么、怎么变、对我有什么影响、什么时候生效、不遵守会怎样
4. **每篇 3-5 条** — 太少不够覆盖长尾词，太多稀释内容质量

**Q&A 节插入位置：** 紧跟在【来源引用】之后。

**格式：**
```
【Q&A】
Q：2026年新加坡EP签证的最低薪资门槛是多少？
A：新加坡EP准证最低薪金门槛从之前的5000新元上调至6000新元（2027年1月生效），金融行业门槛更高，达7000新元。COMPASS积分制对团队多样性提出更高要求。

Q：薪资门槛上调后，对已经在岗的EP持有者是否有追溯效力？
A：新门槛主要影响新申请和续签。现有EP持有者在续签时也需要满足新的薪资标准，未达标可能面临降级或不再续签。

Q：中国企业在申请EP时如何提高获批率？
A：企业需确保薪资达到对应行业门槛，同时通过COMPASS积分制在团队多样性、本地员工比例等维度获得足够积分。建议提前1-3个月准备申请材料。

（FAQ Schema 结构化数据视后续发布渠道决定是否添加）
```

### 9c. 溯源质量硬规则（2026-08-26 新增）

### 9d. ⚠️ 分类比例规则 1:2:1（2026-09-09 固化）

> **为什么写进这里**：这条规则此前**只存在于 3:00 / 15:00 两条 automation prompt 里**，本文件完全没有。prompt 一旦被误改或重建，核心规则就丢了。现固化成本文件唯一真相源，prompt 改为引用本节。

### 14b. ⚠️ 更新已有记录（2026-08-14 踩坑）

**正确做法（两步）：**
1. 拉取记录获取 record_id：

### 14g. ⚠️ 写入前预校验清单（2026-09-04 实测，不做会被 write_records.js 批量拦截）

在生成 JSON 后、调用 `write_records.js` 之前，**必须**先用 Python 模拟一遍校验。以下 4 项是 2026-09-04 实际踩到的坑：

| # | 校验项 | 规则 | 典型踩坑 |
|:-:|--------|------|---------|
| 1 | 标题长度 | **≤30 字** | 超长直接跳过 |
| 2 | 标题前缀 | **禁止** `[XX·高·法规]` 这类前缀 | 前缀会污染相关性滑窗，导致关键词提取全落在 `高`/`法规` 等无意义词上 |
| 3 | 相关性滑窗陷阱 | JS 按 **6→2 字**滑窗提取标题关键词，优先取 6 字词 | 会把「新加坡」「巴林」「埃及」等 2-3 字地名挤掉，导致「标题与正文无相关性」误判 |
| 4 | 敏感词 | 正文**禁止出现「敏感」二字** | 「敏感度分析」会被敏感词正则命中 → 改写为「分档情景测算」 |
| 5 | 法规特征词 | 分类=法规更新时，正文须含：法规/条例/法令/法律/规定/决议/新规/修正案/法案/指令/决定/公告/立法 | 否则判「分类法规更新但无法规特征词」 |

**规避滑窗陷阱的标准做法**：标题用**空格分段**，且每段 **≤6 字**。
- ❌ `巴林8月执法3152次遣返543人` → 滑窗取出「8月执法31」「月执法315」等噪音词，地名「巴林」被挤掉
- ✅ `巴林 8月执法 3152次 遣返543人` → 每段独立提取，「巴林」作为 2 字词直接入关键词集

**Python 预校验模板**（模拟 JS 滑窗逻辑）：
```python
import re
STOP = ['出台','实施','生效','发布','最新','宣布','影响','解读','落地','收紧','调整',
        '改革','全面','正式','明确','规定','中企','中国','企业','出海','合规','政策',
        '新规','变化','意义','分析','推进','升级']
def sim_keywords(title, body):
    segs = [w for w in re.split(r'[【】()（）：:，,。.！!？?《》\-\s]', title) if len(w) >= 2]
    kws = []
    for s in segs:
        if len(s) <= 6:
            kws.append(s)
        else:
            for L in range(6, 1, -1):
                for i in range(len(s) - L + 1):
                    kws.append(s[i:i+L])
    uniq = [w for w in dict.fromkeys(kws) if len(w) >= 2 and w not in STOP]
    core = sorted(uniq, key=len, reverse=True)[:8]
    return core, [w for w in core if w.lower() in body.lower()]
```

### 14j. ⚠️ 双端推送状态对齐（2026-09-04 发现，每次 15:00 校验必做）

**现象**：15:00 校验时飞书侧记录均为「待推送」，但 API 侧部分记录已是 `PUSH_STATUS=1` / `LAYOUT_STATUS=1`。

**根因**：9:00 早报自动化会把对应记录标为 PS=1/LS=1，**但不回填飞书**，导致飞书状态滞后。

**后果**：`insert_records.js` 对已存在记录是「**跳过**」而非「更新」，不会修正已有的 PS/LS 差异。若直接回填飞书「已推送」，会出现**飞书=已推送 但 API=待推送**的语义相反状态。

**标准处理流程**（入库后四步，缺一不可）：

1. **入库**：`node insert_records.js --file xxx.json`（新建 + 跳过已存在）
2. **回填飞书**：`base +record-batch-update --json '{"update_records":{"recX":{"推送状态":"已推送"}}}'`
3. **同步 API 侧**：把飞书已回填但 API 仍为 `PUSH_STATUS=0` 的记录更新为 `1`
   ```js
   p.append('cmd', 'com.awspaas.user.apps.xfsai.knowledge.webapi.update');
   p.append('id', b.ID);                          // BO 记录 ID，非 INFO_ID
   p.append('recordData', JSON.stringify({ PUSH_STATUS: '1' }));
   ```
4. **禁推记录单独同步**：标记「禁止发布」的记录若已在 API 侧，需同步 `PUSH_STATUS=3`

**`LAYOUT_STATUS` 暂不同步**：飞书「待排版」与 API「已排版」（9:00 环节流转）存在差异，因排版流程语义未完全确认，保持原值不动，仅在校验报告中记录为待确认项。

2. 误编 ID 的记录需按 `record_id` 逐个 `+record-delete --yes` 删除（**绝不能按资讯ID删，会误删历史记录**），删除前先 `+record-get` 核对 `更新时间` 为本批次。
3. 法规类记录写完飞书后，若「排版状态」为空，需 `+record-batch-update` 批量补 `待排版`，与 API 侧 `LAYOUT_STATUS=0` 对齐。

### 14m. 🐛 整段替换函数时的误删事故（2026-09-05 15:00 暴露，必读）

### 14m. API 入库链路整改（2026-09-09，QoderWork 方向2 前置清障）

**背景**：归档待办两 bug —— ① API create 静默失败（JSESSIONID 过期返回 result:ok 但数据未入库）② 补跑重复记录（同日二次运行撞号）。根因之一：**15:00 自动化 prompt 步骤八内联 Python 只查 `status_code==200` 就回写「已推送」**，绕过了 `insert_records.js` 的查重+回填验证。

**本次整改（脚本 + prompt + 本文件三处同步）：**

| 项 | 改动 |
|---|---|
| `Claw/next_info_id.js` 🆕 | 只读校验脚本：查询飞书当日最大序号 + 下一 ID（`YYYYMMDDNN` 连续）。`count>0 但 maxSeq=0` = 拉取解析失效，禁止写入。2026-09-09 实测：今日 12 条，next=2026090913 |
| `Claw/insert_records.js` | 新增 `--probe`（只读会话探活，exit 0=有效/3=失效）；新增**会话自动刷新钩子**：create ok 但回填 query 查不到 → 若 `anchortech-config.json` 配了 `session.loginUrl/postData` 则自动重新登录、写回 cookie、重试一次；未配置则 exit(2) 并提示手动刷新。2026-09-09 实测 `--probe`：会话有效 |
| 15:00 自动化 prompt | 步骤七：**补录不手编资讯ID** → 由 `write_records.js` 自动续号 + `next_info_id.js` 核验；步骤八：**统一走 `insert_records.js --file`**（查重/回填验证/会话刷新内置），禁止内联 Python 直连 API；回写「已推送」仅限 ✅已入库/⏭️已存在，❌或 exit=2 保持「待推送」防语义反相 |

**关键语义（防反相）**：`insert_records.js` 对已存在记录是「跳过」不是「更新」——⏭️ 说明 DB 已有该 INFO_ID，同样可回写「已推送」；只有 ❌ / exit=2（未落库）才必须保持「待推送」。

**遗留（需 Yoyo 提供）**：anchortech 登录端点 + 凭据未持有 → `session.loginUrl` 未配置，自动刷新当前走「手动更新 cookie」降级路径；等会话真实过期（或提供登录配置）后做端到端验证。

**2026-09-09 15:50 补充（两件事）**：

**① 配置模板已就位** —— `Claw/anchortech-config.json` 已注入 `session` 占位字段（原文件已备份为 `.bak-YYYYMMDD-HHMMSS`）：
```json
"session": {
  "loginUrl": "",                              // 待填：https://<host>/<登录路径>
  "postData": { "username": "", "password": "" },
  "headers": {}
}
```
填好即可启用自动刷新。**`loginUrl` 留空时脚本行为不变**（走手动刷新降级，`refreshSession()` 检测到无 loginUrl 直接返回 false，绝不猜登录接口）。

**② ⚠️ 失败必须告警（不依赖凭据，立即生效）** —— 自动刷新短期做不了，但**静默失败没人知道**才是当前最大风险。故补硬规则：

> **`insert_records.js` 以 exit code = 2 结束时，必须立即发飞书 P0 告警，不能只写在校验报告里。**
> 告警内容：`【P0告警】Anchor Tech 会话失效，N 条记录未入库｜修复：浏览器登录 anchortech.ai 后更新 Claw/anchortech-config.json 的 cookie，或补齐 session.loginUrl 配置｜修复后重跑自动跳过已入库记录（幂等）`
> 发送方式：优先 QC 告警通道（调用 `yoyo-qc-auditor` 技能登记并通知 Yoyo）；未配置时发到飞书群并标注【P0告警】。
>
> **理由**：exit(2) 意味着「create 返回 ok 但数据根本没进库」——这是本次整改要消灭的静默失败。如果只是写进报告，Yoyo 不主动看就等于数据丢了没人知道。

**对旧缺陷表第 1 条的影响**：步骤八改从飞书回读组装 `api_records.json`（含 INFO_ID），不再依赖「records JSON 预填 ID」的规避 → 3AM 链路的预填做法保留不动（A1 侧），15:00 侧已不依赖它。
