# 历史项目收敛 · 总纲 + 作战图

## 适用场景

一个改造/优化项目已经推进了一段时间，需求散在飞书、原型 HTML、说明 md 里，**同一件事有多份文档、口径互相冲突**。用户要求「整理一份当前文档 + 需求清单 + 相关设计图 + 分配工作」。

产出**两份**交付物：
1. **总纲文档（.md）** —— 唯一真相源。类目 / 需求清单 / 资产指针索引 / 工作分配 / 待拍板。
2. **作战图（.html）** —— 总纲的**受控副本 + 可视化**。单文件、四视图、可筛选。

---

## 六步流程

### 第 1 步 · 锁定需求源头

先把「谁说了算」定下来。常见源头：飞书 wiki/docx、用户口述、历史 md。

```bash
# 飞书 wiki 节点（拿 obj_token / 标题）
lark-cli wiki +node-get --node-token "<wiki url>" --format pretty

# 取正文：⚠️ 用 URL，不要用 node-get 拿到的 obj_token，+fetch 不认
lark-cli docs +fetch --doc "<wiki url>" --format pretty
```

> 若 `+fetch` 报 `unknown flag`，看 `lark-cli docs +fetch --help` 的 flag 清单——不同版本参数名不同（`--doc` 而非 `--doc-token`）。

### 第 2 步 · 扫全资产（不要漏、不要复制）

资产通常散在**多个工作区**。按时间倒序找近 1 个月的原型：

```bash
find /Users/yoyo/WorkBuddy -maxdepth 4 -iname "*.html" -newermt "<起始日>" 2>/dev/null \
  | grep -viE "node_modules|\.git/" | head -40
ls -la "<各工作区>/outputs/" | grep -iE "原型|设计|UI|流程|landing|prototype"
```

登记每份资产的：**绝对路径 / 覆盖哪条需求 / 能直接给谁用**。

> 🔴 **绝对不复制资产文件**。只登记指针。复制会产生多副本，下次只改一份 → 口径漂移。

### 第 3 步 · 归类目 + 做裁定

以**需求源头**的类目为主干（如飞书的 8 大项），把历史文档里的需求逐条归位。

**必做**：找出历史文档之间**互相冲突**的条目，显式写下裁定结果与理由：

```markdown
> ⚠️ **口径裁定**：09-11 版写「X」，09-15 版与源头写「Y」→ **裁定以源头为准**。理由：……
```

不写裁定的后果：两个人照着两份文档做出两个东西。

**同时检查归类是否合理**：源头里被放在「内容」类目下的**线索承接位 / 商业动作**，应拆出来独立成线——否则会被内容排期挤掉。

### 第 4 步 · 分主线 + 切工作包

按「改造目的」而非「页面」分 2–4 条主线（如：① 转化链路修复 ② 内容与资料供给 ③ 工具与商业承接）。

再切成工作包，每个必须给全四项：

| 字段 | 说明 |
|---|---|
| 负责 | 具体角色（需求 / UI / 前端 / 数据 / 内容 / 法务） |
| 输入 | 从哪份文档、哪条需求出发 |
| 交付物 | 可验收的产物形态 |
| 依赖 | 卡在什么上（**待拍板事项必须在这里显式指向**） |

> 用户团队有「文达（PRD）→ 简一（UI 原型）→ 前端」的协作链时，把需求梳理与 UI 设计分成两条独立工作流。

### 第 5 步 · 写总纲（.md）

固定骨架，别自由发挥：

```
〇 这份文档解决什么问题（含统计条：类目/需求/资产/工作包/待拍板）
一 改造总览（一句话定位 + 主线表 + 类目地图表）
二 需求清单（逐条：编号 / 需求 / 验收要点 / 梳理态 / 设计态 / 开发态）
三 设计资产索引（指针式，分：可交互 HTML / 说明文档 / 可合入代码 / 资产缺口）
四 工作分配（工作流表 + 工作包表 + 启动顺序）
五 优先级汇总（P-1 / P0 / P1 / P2）
六 待拍板事项（含"卡住谁"）
七 资产唯一性声明
```

**需求条目三态标注**用 ✅ 已完成 / ⚠️ 待确认 / ⬜ 待办，让读者一眼看出进度。

### 第 6 步 · 写作战图（.html）

单文件、无外部依赖、与项目既有原型**共用同一套 CSS 变量与字体**（别引入新视觉体系）。

必备：
- 头部统计条 + 三主线卡
- **四视图切换**：类目与需求 / 设计资产 / 工作分配 / 启动顺序
- 类目卡可折叠、可按主线与优先级筛选
- 状态点图例、优先级徽章
- footer 声明「本页数据为总纲第 X 节的受控副本，冲突以总纲为准」

数据内联为 JS 常量数组（`CATS` / `ASSETS` / `WPS` / `WAVES` / `DECIDE` / `GAPS` / `FLOW`），渲染用模板字符串。

## 四条纪律（最重要）

1. **资产不复制，只登记指针** —— 设计图只有一份，索引给出绝对路径与覆盖范围。
2. **看板是衍生物** —— 允许看板存在一份机器可读副本，但必须在**三处**声明主从：看板文件头注释、看板 footer、总纲声明节。写明"修改需求只改总纲，再同步看板"。
3. **冲突必须显式裁定** —— 发现两份文档口径不一致，不能沉默取其一，要写出「裁定 + 理由 + 谁为准」。
4. **聚合页放哪由「预览静态根」决定，不由分类美感决定** —— WorkBuddy 预览面板**只暴露被预览文件所在目录及其子树**，向上（`../`）会 404。所以：
   - **跨目录索引**（要同时收 `A/` 与 `B/` 两个平级目录）→ **放到两者共同父级**，内部写 `A/x.html`、`B/y.html`。
   - **页内要内嵌真身**（宿主页用 iframe 装另一份原型）→ **真身必须与宿主页同子树**，必要时把真身目录**迁到宿主同级**，而不是写 `../` 赌它在预览里能解析。
   - 判断口诀：**"我要 iframe 谁 / 链谁，它是不是在我这棵子树里？"** 不是 → 要么放共同父级，要么迁进来。
   - 迁移后**必须两查**：① 谁引用了这批文件（外部引用）② **这批文件之间的相对互链**（内部互链）——只查前者是经典漏网（实测：工具间 38 处互链全断，外部引用却都正常）。

## 自检清单

```bash
# ① 结构：标签闭合 + script 内无 </script> 提前终止
# ② 数据：常量数组条数与预期一致
# ③ 引用：getElementById 的 id 在 HTML 中都存在
# ④ 统计：header 数字必须从渲染结果反推，不能手写
```

**必查项**：
- [ ] header 统计数字 = 实际渲染条数（常见错：手写「8 类目」但实际渲染 9 张卡）
- [ ] `script` 内若含 `<style>`/`<head>` 等文本，确认没有 `</script>` 字样提前闭合
- [ ] 每个工作包的「依赖」都能追溯到具体待拍板事项或前置工作包

## 踩坑记录

| 坑 | 现象 | 解法 |
|---|---|---|
| **hash 锚点劫持滚动** | 用 `#v-assets` 做视图直达，浏览器滚到同名 id 元素，首屏被切掉 | hash 加前缀改为 `#view-v-assets`（页面无同名 id），浏览器不再锚点滚动。`history.replaceState` 本身不触发滚动，只有首次带 hash 打开才会 |
| 统计数字手写 | header 写「8 类目 / 42 需求」，实际 9 卡 / 57 条 | 渲染完用脚本数一遍再回填 |
| 卡片等高留白 | grid 默认 stretch，让同行卡片等高，短卡下方一片空白 | `.cats{display:grid;align-items:start}` |
| lark-cli 参数名 | `+fetch --doc-token` 报 unknown flag | 用 `--doc`；先跑 `--help` 确认该版本参数 |
| 预览服务注入属性 | present_files 后 HTML 被注入 `data-page-node-id` | 交付前清理：`re.sub(r'\s*data-page-node-id="[^"]*"','',s)` |
| **子目录里写 `../` 内嵌真身 → 预览 404** | 宿主页在 `site/`，真身在平级 `tools/`；本地 file:// 正常，预览面板里 iframe 全白 | 真身**迁到宿主同子树**（`site/tools/`）；迁完按纪律 4 查外部引用 + **内部互链** |
| **多份清单各自维护 → 必然漂移** | 卡片按钮、切换下拉、纵览区块、深链各写一份工具名单，加一个工具要改四处 | **一份 `REAL` 映射驱动全部 UI**（按钮/下拉/chips/纵览/深链），加工具只加一行；`wireReal()` 里加幂等判断（`if(cta.querySelector('[data-open]')) return;`） |
| 截图「多张图字节完全相同」 | 无头下页面根本没滚动 | 源页含 `scroll-behavior:smooth` → 驱动页在 `eval` 前注入 `html,body,*{scroll-behavior:auto !important}` |

## 后续维护

- 飞书源头更新 → 同步总纲对应条目 → 再同步看板 JS 数组（**这个顺序不能反**）。
- 建议把总纲第二节的需求表搬进飞书多维表做进度跟踪（含状态列 + 负责人列），实现一处更新处处可见。
