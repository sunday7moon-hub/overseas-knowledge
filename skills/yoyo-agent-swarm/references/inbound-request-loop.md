# 入站指令闭环（Inbound Request Loop）

> 建立日期：2026-09-21 ｜ 起因：飞书群「@巴蒂」指令反复出现「已读未执行 / 产出未投递」
> 定位：**这是 `yoyo-agent-swarm` 缺失的入口环节**。现有六步流程从 Step 1「意图识别」开始，
> 但入口处没有任何东西保证「群里的指令」变成一个**可追踪、可续传、可验收的实体**。

---

## 一、问题定义

### 现象（有据可查的三次复发）

| 时间 | 群 | 原话 | 实际状态 |
|---|---|---|---|
| 2026-09-15 14:27 | 慧思出海资料 | 「这些素材同步飞书表格了吗？@巴蒂」 | 素材已生成，未落表 |
| 2026-09-16 10:10 | 慧思出海资料 | 「你出的还是小红书文案不是微信群分享【知识卡片】」 | 交付形态错，无人校验 |
| 2026-09-21 10:59 | 慧思出海资料 | 「图片没同步飞书群」 | 卡片已生成，未投递 |

### 根因（三层，逐层往下）

1. **完成判据错位（最直接）**
   把「素材已生成 / 文案已排」当完成。真实 DoD 是「**已投递到目标载体 + 回读校验通过 + 已回执**」。
   生成 ≠ 交付；落在本地磁盘的东西，对客户和 Yoyo 都等于不存在。

2. **无请求实体（导致不可续传）**
   群消息被"读进上下文"就完事，没有落成一行台账。
   状态只存在于会话内存里 → 会话一断，待办蒸发 → 这正是「WorkBuddy 断了重启后交付断链」的机制性原因。

3. **无回执闭环（导致双方认知不一致）**
   执行完不在原消息下回报。Yoyo 看到"已读"无法区分「在办 / 已办 / 漏了」，只能反复追问。

### 与既有纪律的关系

这是 Yoyo「防转述丢失」纪律的**同族问题**：
事实（待办状态）只活在**易失层**（会话上下文），没有落进**真相源**（台账）；
而"清单没有变成门禁"——历次口头强调「记得投递」从未生效过，**只有门禁才防复发**。

## 二、机制（三件套）

### 2.1 请求实体化：一条入站消息 = 一行台账

**核心判据：没入台账的承诺 = 不存在。**

凡是「@巴蒂 + 祈使句」的消息（出X、同步X、查X、改X），一律先落台账再干活。
落台账的动作不因"事情很简单"而豁免——**简单任务正是漏得最多的**。

### 2.2 DoD 矩阵：完成判据显式化

每类请求的完成判据写死在台账 `完成判据` 字段里。**全中才算完成，缺一即「待投递」。**

| 请求类型 | 完成判据（DoD，全中才可置「已回执」） |
|---|---|
| 出卡片 / 海报 | ①图片已生成 ②**已发目标群** ③配套文案已发 ④原消息下回执 ⑤回读校验通过 |
| 出早报 / 日报 | ①内容已编排 ②已发目标群 ③链接可点开 ④回执 |
| 出报告（PDF） | ①过技术门禁 ②过内容门禁 ③已投递客户渠道 ④回执 |
| 同步到飞书表格 | ①记录已写入 ②回读条数校验 ③回执 |
| 内容发布（前端/三方） | ①已发布 ②线上可访问校验 ③回执 |
| 客户群需求 | ①入「客户交付台账」②已回复客户确认 ③交付物已投递 ④回执 |

> **"已生成"永远不是 DoD 的一部分。** 它只是前置条件，不计入完成度。

### 2.3 状态机

```
待接单 → 已确认 → 执行中 → 待投递 → 已投递 → 已回执 → 已归档
                    ↓          ↓
                 阻塞(等外部输入)  返工 → 执行中
                    ↓
                  已作废
```

**只有 `已回执` 及之后才是完成态。** `已投递` 仍需回读校验确认。

## 三、断点续传协议（核心）

任何会话 / 自动化启动的**第一步**（早于所有业务动作）：

```bash
python ~/.workbuddy/skills/yoyo-agent-swarm/scripts/inbound_ledger.py pending
```

输出所有 `状态 ∉ {已回执, 已归档, 已作废}` 的请求。**有未完成项 → 先续做，再接受新指令。**

续传三原则：
1. **先扫后干**：任何新会话的第一条命令是 `pending`，不是「你好」。
2. **双写**：台账（跨会话真相源）+ 工作区当日 memory（上下文）。台账为准，memory 作补充。
3. **幂等投递**：投递类动作带 `--idempotency-key`。续传时重跑不会造成重复发送。

## 四、门禁（写进流程，不靠自觉）

在 `yoyo-agent-swarm` 六步流程前后各加一道：

| 位置 | 门禁 | 不过的处置 |
|---|---|---|
| 入口（Step 0 后） | 本会话收到的祈使句指令，是否都已落台账？ | 补落后再开工 |
| 出口（Step 6 后） | 本次涉及投递的请求，`完成判据` 是否逐项验过？ | 置「待投递」，不得报「完成」 |

**自检问句（每次收尾必答）**：
> 「我说了'完成了'，但如果现在重启一个会话去群里看，能不能看到东西？」

答否 = 没完成。

## 五、台账字段（唯一真相源）

飞书多维表「客户交付台账」（与 `yoyo-agent-swarm/scripts/config.json` 的 base 同库）：

| 字段 | 说明 |
|---|---|
| 请求ID | `REQ-YYYYMMDD-NN` |
| 客户 / 账号 | 归属客户（内部场景填"内部"） |
| 角色 | 提需求的人的角色（HR负责人/招聘经理/财务/法务/决策者…） |
| 需求线 | thread_key，**可多值**，见 `client-delivery-steward` |
| 来源 | 群 / 私聊 + 消息ID 链接 |
| 原始诉求 | 客户原话**逐字**（不写概括，防口径漂移） |
| 完成判据 | DoD 文本，取自 §2.2 矩阵 |
| 状态 | 状态机取值 |
| 优先级 | 🔴P0 / 🟡P1 / 🟢P2 |
| 阻塞原因 | 旁支状态时必填 |
| 产出路径 / 链接 | 交付物位置 |
| 回执消息ID | 闭环证据 |
| 更新时间 | 自动 |

## 六、脚本

`scripts/inbound_ledger.py`

```bash
# 建表（首次）
python inbound_ledger.py init

# 落一条请求
python inbound_ledger.py add --json '{"客户":"慧思","角色":"运营","需求线":"慧思-卡片","原始诉求":"@巴蒂 出今天的日报","完成判据":"①内容已编排 ②已发目标群 ③链接可点 ④回执","优先级":"🟡P1","来源":"oc_e9daf25...|om_xxx"}'

# 更新状态
python inbound_ledger.py update --request-id REQ-20260921-01 --json '{"状态":"已回执","回执消息ID":"om_xxx"}'

# 断点续传扫描（会话启动第一步）
python inbound_ledger.py pending

# 投递回读校验：确认某条消息确实在群里
python inbound_ledger.py verify --chat-id oc_xxx --message-id om_xxx
```
