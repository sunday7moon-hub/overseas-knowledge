# 国别指南「更新标注」规范（六要素 + 页面落位）

> 用途：把校对出的差异**落到线上页面的正确位置**，且不破坏已发布内容。
> 来源：2026-09-21 与 Yoyo 确立，承接 2026-09-07 B2-01 校对成果。
> 定位：本文件是 `humance-content-baseline`（只读盘点）的**下游输出规范**——盘点+校对产出差异，本规范规定差异怎么表达。

---

## 一、为什么是「标注」而不是「直接改」

2026-09-07 B2-01 校对出 117 条差异；2026-09-22 **Strapi 写权限 Token 已到位**，凭据存 `~/.workbuddy/.humance_strapi_token`（chmod 600）。
但**即便有写权限，数值类变更仍走「标注」而非直接改正文**——因为数值需人工确认，未经确认不能改坏线上已发布内容。

**核心红线：数值类变更只进标注块，不改正文表格数字。** Token 到位后，人工确认过的条目才把标注转正为正文值。

> 实测：标注块**纯新增、不改原值**，即使写错也可从 `_strapi_backup/` 的 ORIGINAL 一键回滚，风险远低于直接改数。

### 状态判定规则（2026-09-23 修订，同日改为**客户向文案**；配色同日重定）

状态是**两个正交维度**，不允许混为一谈：

| 维度 | 取值 | 判定口径（唯一实现 = `effective_state()`） |
|------|------|------|
| **页面更新状态** | `pending` 待更新 / `check` 待核 / `keep` 无需更新 | 由批次配置人工定：正文是否还需要改 |
| **法规生效状态** | `effective` **已正式生效** / `scheduled` **计划变更** / `na` 不适用 | **生效日 vs 标注写入日**；生效日 ≤ 写入日 = 已生效（**当日生效算已生效**）；无可解析日期 = 不适用 |
| **配色档**（新增） | `in_force` 绿 / `upcoming` 橙黄 / `verify` 红 / `no_change` 绿 | `tone_of(note)`：**按「变更落地进度」着色，不按 status 着色**（唯一实现 = `guide_patch_lib.TONE` + `tone_of()`）；**四档 tone 值、三种颜色** —— 两个绿档同色值 |

组合后的页面文案（`render_note` 自动生成，**不允许手写**）：

| 页面更新状态 | 法规生效状态 | 徽标 | 配色档 |
|---|---|---|---|
| 待更新 | 已正式生效 | `⏳ 待更新 · 已正式生效` | **`in_force` 绿** |
| 待更新 | 计划变更 | `⏳ 待更新 · 计划变更` | **`upcoming` 橙黄** |
| 待更新 | 不适用 | `⏳ 待更新`（**会被 E1 门禁拦下** —— 待更新必须有可解析生效日） | `upcoming` |
| 待核 | 任意 | `⚠️ 待核（来源存疑）` | `verify` 红 |
| 无需更新 | 任意 | `✅ 无需更新` | `no_change` **绿（与上面第二行同色，靠文案区分）** |

#### 配色规则（Yoyo 2026-09-23 定，同日两次修订 —— **以 v3 为准**）

原实现是**颜色跟 `status` 走**：`pending` 橙、`check` 红、`keep` 绿。问题在于 —— 绿同时表示「有更新」和「没更新」，绿就失去了信息量；
而「有变更且已生效」这个客户最需要一眼看到的状态，反而没有专属颜色。

现改为**颜色跟「变更落地进度」走**，口径经过三次迭代：

| 版本 | 口径 | 为什么被改掉 |
|:-:|---|---|
| v1 | 颜色 = `status` 的代理 | 绿被滥用成"打勾通过"，客户分不清**有变更已落地**与**本来就没变** |
| v2 | 绿只留给「今年有变更且已生效」；维持现状 → **中性灰** | 灰在中性语境下像"没做完 / 被跳过"，客户会以为是漏处理的章节 |
| **v3（现行）** | **维持不变也标绿**（Yoyo：「还有继续维持不变，也是绿色」） | 客户视角下「已核实、无需关注」**就是一档**，不必在绿色内部再分深浅 |

**v3 的色义**：

| 档 | 色 | 语义 | 触发 |
|:-:|:-:|---|---|
| `in_force` | **绿** `#22c55e` | 今年**有**变更，且**已正式生效** | `status=pending` ∧ `effective_state()==effective` |
| `no_change` | **绿** `#22c55e`（**同一份色值**） | 核实后**维持现状** | `status=keep` |
| `upcoming` | **橙黄** `#f59e0b` | 确定今年**计划**变更，**尚未生效** | `status=pending` ∧ 其余（含生效日待定） |
| `verify` | **红** `#ef4444` | 来源存疑，**待核** | `status=check` |

> **两个绿档靠文案区分，不靠颜色**：`⏳ 待更新 · 已正式生效`（写明改了什么） vs `✅ 无需更新`（写明核过了、没变）。
> 客户要一眼看到的是「哪一章还要关注」（橙黄 / 红），不需要在"不用管"里再分两档。
> `tone` 值本身仍保留两份 —— 台账与 `data-cg-tone` 属性需要区分「改过且已生效」与「核过没变」。
>
> **章节级配色**（h2 徽标 / 左侧目录气泡，唯一实现 `section_tone()`）：一章多标注时取**最先要处理的那一档**（待更新 > 待核 > 无需更新）；
> 且该章 `pending` **全部**已生效才给绿 —— 只要还有一条未生效，整章标橙黄（绿 = 这一章的变更全落地了，别让一条未生效的藏进去）。
>
> **色值不许手抄**：标注块与徽标 CSS **从 `TONE` 生成**（`_badge_css()` 亦然），
> 且 `in_force` / `no_change` **共用 `GREEN` 一份常量**（`dict(GREEN)` 浅拷贝）——
> **改绿只改一处**。色值抄两份必然漏改一处（「防转述丢失」纪律）。
>
> 门禁 = QC 的 **E3**（`data-cg-tone` 必须等于 `tone_of()` 重算值）+ **`selftest_gates.py` 的 F11 / F11b**
> （把「维持不变 = 已生效 = 绿」这条业务口径钉住 —— 口径再变必须同时改测试，让改口径成为一个**显式动作**）
> + 真渲染验证（实测各档实际渲染色）。

> **文案常量唯一真相源 = `guide_patch_lib.STATUS_TEXT`**（`{"pending": "⏳ 待更新", "check": "⚠️ 待核", "keep": "✅ 无需更新"}`）
> 与 **`EFF_TEXT`**（`{"effective": "已正式生效", "scheduled": "计划变更", "na": ""}`）。
> 渲染层 / 预览层 / 通知正文 / E·F 组门禁探针**全部引用它**，谁都不许另写一份中文字面量。
> 已被替换的旧文案（`已核实维持` / `计划更新` / `法规已生效` / `计划生效`）收进 `guide_patch_lib.STALE_COPY`，
> 出现在产物里即由 **F3** 判不合格 —— 这是防旧稿回流的关键（产物是长期存在物，常量改了防不住旧稿被重新推上去）。

> **「✅ 已核实维持」→「✅ 无需更新」的改名理由**（Yoyo 2026-09-23：「这个状态也有点奇怪」）：
> ① 「已核实」是**过程语言**（我方做了什么），不是**结论**（客户要知道什么）；② 「维持」的参照物客户看不见（维持什么？跟哪个时间点比？）；
> ③ 与同一行的元信息「生效日期 —（维持现行）」语义重复，等于一句话说两遍。
> 新文案 `✅ 无需更新` 是 `⏳ 待更新` 的同构反义 —— 两个状态在同一句法里对照，客户一眼能分清。

> **为什么必须带前缀、不能只写「已生效」**：`已正式生效` 说的是**法规本身**已落地；裸的「已生效」会被读成**页面正文**已更新。
> 页面正文在标注机制下始终未改（原值只增不减，三条渲染红线之一），所以裸的「已生效」是错的表述。
>
> **为什么用「已正式生效 / 计划变更」而不是「法规已生效 / 计划生效」**（Yoyo 2026-09-23：「写这个是给客户看的」）：
> 页面读者是出海中企 HR，不熟悉我方内部口径。旧词带内部编辑味，`计划变更` 也更准确 —— 变的是**法规**，不是页面。
>
> **触发场景（Yoyo 2026-09-23 反馈）**：MR 340/2026 生效日 2026-06-01，线上却显示「计划」——实际早已生效。
> 根因是旧口径把「页面要不要改」当成「法规生不生效」。现由 `effective_state()` + E1/E2 门禁强制对齐。

### 内部过程字段：只进台账，不上页面（2026-09-23 定，分三轮撤净）

Yoyo 的截图先后圈出三处：

| 轮次 | 圈出的位置 | 字段 |
|:-:|---|---|
| 一轮 | 标注块底部那串 | `标注写入：2026-09-23 ｜ 校对 ID PR-20260907-046` |
| 二轮 | 同上（首轮漏了一个） | `页面位置：薪酬支付` |
| 三轮 | **版本条尾部** | `校对批次 B2-01-T-migrate` |

它们是我方**编辑过程留痕 / 生产工单号**，客户看了只会困惑（「谁写的？PR 是什么？」「B2-01-T-migrate 是什么系统的东西？」，以及「页面位置」在我方自己的页面上是废话），**必须撤出页面**。

| 字段 | 页面 | 台账 | 机器定位 |
|---|:-:|:-:|---|
| `标注写入：<日期>` | ❌ 不显示 | ✅ `更新时间` 列留档 | — |
| `校对 ID PR-xxxxxxxx-nnn` | ❌ 不显示 | ✅ `校对ID` 列留档 | **`data-cg-rid="PR-…"` 属性** |
| `页面位置：<章节标题>` | ❌ 不显示（二轮撤出） | ✅ `落位章节` 列留档 | **`data-cg-anchor="…"` 属性** |
| `校对批次 B2-01-T-migrate` | ❌ 不显示（三轮撤出） | ✅ `校对批次` 列留档 | —（批次是整批评次，非单条定位用） |

**做法：把可见文字换成 HTML 属性。** 属性不在 `textContent` 里，客户看不见、复制也复制不到；
但 `querySelectorAll('[data-cg-rid]')` 依然能数、能取，所以 T4（校对ID 齐全唯一）、
S4（集合一致）、`migrate_existing.py`（从线上反抽旧标注）全部改成读属性，一条都没丢。
`data-cg-anchor` 同理承载「落位章节」—— 台账要回填该列时直接从属性取，不依赖页面可见文字。

> **唯一真相源**：`guide_patch_lib.INTERNAL_FIELDS = ["标注写入", "校对ID", "校对 ID", "页面位置", "校对批次"]`。
> 三道闸门（`validate()` 的 **F4**、`qc_gate.py` 的 **F4**、`verify_secondary.py` 的 **S13**）
> 全部 import 这一个常量，谁也不许另写一份字符串。
> 判据同 §18：**「我想改这个字段清单，要动几个文件？」—— 答案是 1。**

> ⚠️ **教训：「撤出页面」要一次做全。** 同一张截图上圈了几个字段就撤几个 ——
> 漏一个就要再走一轮（页面位置、校对批次各补过一轮），而下线返工的成本远高于当初看全。
> 现在这条清单由门禁把守，**旧稿回流会被 N14（qc_gate）/ S13（全文校验）拦下**，不再依赖人眼复查。

> ⚠️ 与 F2 的分工：**F2 管时间**（`校验时间` / `最新校验` / `校对日期`），**F4 管字段名**（`标注写入` / `校对ID` / `页面位置` / `校对批次`）。
> 两者都属「客户向文案」组，都是阻断项，但探针不同 —— 别合并，否则以后加字段会漏。

> 行内 `style` 全部保留（平台会剥 `<style>` 块，行内样式才不会被丢）。**块内一律不用 `<div>`**（§15.3）。

```html
     data-cg-status="pending" data-cg-eff="effective" data-cg-effective="2026-06-01">
  <p>⏳ 待更新 · 已正式生效　WPS 工资保护新规</p>

  <p>本节表格中「私营企业次月 10 日前支付」为 MR 598/2022 旧口径…</p>
</div>
```

**四个 `data-cg-*` 属性的分工**（属性是给机器看的，客户看不见）：

| 属性 | 作用 | 谁在读 |
|---|---|---|
| `data-cg-rid` | 校对ID —— **替代页面上可见的「校对ID PR-…」**，只落台账不留文字 | T4 / S4 / `migrate_existing.py` |
| `data-cg-status` | `pending` / `check` / `keep` | 徽标计数、T7 |
| `data-cg-eff` | `effective` / `scheduled` / `na` | **E2**（与按生效日重算比对） |
| `data-cg-effective` | 生效日期原值 | E1 / E2 |

> ⚠️ meta 行**只有这一种写法**。曾经的 `标注 2026-09-21 ｜ 校对ID PR-…` 已被 F4/S13 判不合格
> （见 §2「内部过程字段」）—— 客户看到「谁写的、PR 是什么」只会困惑。

## 四、三条渲染红线

| 红线 | 说明 |
|------|------|
| **不删原值** | 现行值必须保留在标注块内，读者能看到「从什么变成什么」 |
| **不写「已生效」** | 未回写、未人工确认前只能是 `⏳ 待更新` |
| **数值类不进正文** | 正文表格与段落数字零改动，变更只在标注块内表达 |

## 五、双通道更新机制

| 通道 | 触发 | 时效 |
|:----:|------|------|
| **L1 一次性批量** | 承接校对批次（B2-01…B2-05），批量生成标注 | 按批次窗口 |

## 十一、前端渲染模型 ★★（2026-09-22 读前端源码确认，本技能最重要的一条约束）

阿联酋试点时发现：标注落库了、API 侧全对、内容逐字节可还原，**但线上页面看不到**。
读前端产物（`/assets/SafeHtmlRenderer.*.js`、`/assets/ContentUpdater.*.js`）后确认根因。

### 11.1 事实：详情页是「按章节分页渲染」，不是整篇渲染

1. 目录里每个章节是**独立 URL**（`…/国家概况`、`…/薪酬支付` …，共 12 个）。
2. 前端拿到整篇 `content` 后只做三件事：
   - 定位 `<div class="main-container">`，取它的**顶层子 div** 列表；
   - 取「第一个 `<h2>` 文本 == 当前章节名」的那个 `content-section`；
   - 套进一段**硬编码骨架**，再 `innerHTML` 渲染。
3. 骨架形如：

```html
<!DOCTYPE html><html lang="zh-CN"><head>
  <meta charset="UTF-8"> … <title>国别指南</title>
  <link …font-awesome…><link …fonts…><link …blue.css…>   <!-- 仅 3 个外链，没有我们的 <style> -->
</head><div class="nrz"><div class="main-container">

${匹配到的那个 content-section}

  </div></div></html>
```

（登录态由 `ContentUpdater` 走同一骨架并替换 `.article-content`；未登录由 `SafeHtmlRenderer` 渲染未登录预览。两者都不做 HTML 白名单过滤 —— 只是**骨架里没有我们注入的东西**。）

### 11.2 由此得出的三条硬规则

| # | 规则 | 违反后果 |
|---|---|---|
| 1 | **任何要显示的元素必须放在 `content-section` 内部** | 放 `.nrz` 下或 `main-container` 顶层 → 被骨架丢弃（版本条曾整块消失） |
| 2 | **不要依赖注入 `<style>`**（骨架的 `<head>` 是硬编码的） | 样式不生效（章节徽标曾空白）。必须把 `<style>` 放进**每个需要它的章节内部** |
| 3 | **优先用内联样式/属性** | 内联样式随章节一起被搬进骨架，最稳（标注块就是这样才活下来的） |

对应落地：**版本条注入每一个 `content-section`**（12 份副本，因为 12 个 URL 各自渲染）；
**徽标样式块注入每个含标注的章节**；标注块本来就在章节内 → 无需改。

### 11.3 这条约束顺带解释了两件事

- 上一轮「版本条被 `.nrz{display:flex}` 挤到页面底部」的诊断**是错的** —— 那是本地整篇渲染的假象。
  线上从不整篇渲染，真实症状是「被骨架丢弃」。`guide_patch_lib` 里已删掉基于该错误前提的检查，换成 §11.4 的门禁。
- 「徽标文本不能写进 `<h2>`」这个决定**必须继续坚持**，而且理由更强了：
  前端用 `h2` 文本做**章节匹配**（`o===target` 或互相 `includes`）。文本里塞徽标会让匹配变脆，TOC 也会脏。

### 11.4 新增门禁：前端分章模拟（`simulate_frontend_section()`）

`guide_patch_lib` 已内建前端算法的 Python 复刻，`validate()` 会：

1. 取 content 里全部 12 个章节名，**逐章**模拟前端骨架渲染；
2. 每章断言：**版本条存在**；
3. 含标注的章节额外断言：**标注块数量相符**、**徽标属性存在**、**`::after` 样式块没被丢弃**；
4. 另有正向检查：版本条**不得**成为 `main-container` 的顶层子元素。

> 这条门禁的价值：静态 HTML 校验全绿也证明不了"线上看得见"。**能证明"看得见"的，只有把前端的搬运逻辑复刻过来跑一遍。**

### 11.5 另一个平台行为：`previewContent` 由平台从 `content` 派生

- **PUT `previewContent` 无效**。实测：提交 7,407 字节的预览 → 存回 6,621 字节，且**存回值逐字节等于 `content` 的前缀**，而不是提交串的前缀；两次 apply 提交完全不同的预览、`content` 相同 → 存回值完全相同。
- 派生截断点固定在 `content` **约 6.5KB 字节**处，恰好切在《国家核心信息速查表》中间，产生 `…首都</s` 这类**半截标签**。这是**平台侧缺陷**，我们改不了（曾试图写"按标签边界收尾的预览"，实测无效，属假修复，已删）。
  → 未登录可见的那一段会带这个瑕疵；**要修得找平台/前端侧**，不要在落标脚本里再折腾。
- `content` 落库时平台还会给 `<style>` 里的选择器注入 `.article-isolate ` 作用域前缀（+93 字节）。
  ⇒ **落标回查不能直接比 sha**（会永远 False 假阴性），必须先剥掉 `<style>` 再比 —— 用 `L.verify_content()`。

### 11.6 缓存与生效节奏

- 内容层（`admin.humancehr.com` API）**立即生效**，可随时回查。
- 前端页面 HTML 有独立缓存：落标后短时间内访问仍会看到旧载荷（实测同一 URL 字节数不变、载荷内仍是旧结构）。
  ⇒ **不要把"页面还没变"当成落标失败**。判定口径：**API 侧等价 + 分章模拟通过 + 真渲染通过 = 已落地**；页面侧等缓存自行过期后再复核。
- ★ **复核技巧：给 URL 加随机 query 参数可绕过边缘缓存**（2026-09-22 实测）。
  URL 形状是 `/country-guide/<slug>/<章节名>`（无参数访问 `/country-guide/<slug>` 会 302 到第一章）：

  ```bash
  U="https://www.humancehr.com/country-guide/<slug>/%E5%9B%BD%E5%AE%B6%E6%A6%82%E5%86%B5"   # 国家概况
  curl -s "$U?nocache=$RANDOM" | grep -c '@scope (.table-of-contents)'   # 新版应 >0
  curl -s "$U"                 | grep -c '@scope (.table-of-contents)'   # 无参数可能命中旧缓存 → 0
  ```

  实测：加 `?nocache=…` 抓到的 HTML 里 `@scope` 块数 >0、旧版被加前缀的规则 = 0，**说明服务端渲染已是新版**，
  只是无参数 URL 被 CDN 缓存了旧 HTML。`curl -sI` 看不到 `Cache-Control` / `Age`（只有 `x-waf-uuid`），TTL 不可控 ——
  所以「线上还没变」时**先带 query 复核一遍**，别急着重复 apply。

## 十二、来源溯源规范 ★（2026-09-22 阿联酋 6/6 实测落地）

### 12.1 为什么要做

标注块里的「原文链接」如果指向律所解读、行业平台汇编或媒体转载，**对客户不成立**：
客户拿这份内容去做合规决策时，需要的是**能直接引用的官方原文**。二手源的典型问题：
① 转述可能失真；② 原文修订后不会跟；③ 客户法务不认。

### 12.2 三档来源分级（判定口径）

| 档 | 类型 | 举例 | 处置 |
|:-:|---|---|---|
| **L1 一手源** | 法规原文 / 部门官方新闻稿 / 官方门户页 | `mohre.gov.ae` 决议 PDF、`u.ae` 政府门户、`uaelegislation.gov.ae` 联邦立法门户、`gpssa.gov.ae` | ✅ 直接作为「来源」，标 **官方原文 ↗** |
| **L2 官方渠道** | 国家通讯社、官方公报 | WAM（阿联酋国家通讯社）、Official Gazette | ✅ 可用；优先 L1 若可得 |
| **L3 二手源** | 四大·律所解读 / 行业平台汇编 / 媒体转载 / 当地律所 | Morgan Lewis、Teamed、Morgan Lewis、Kayrouz & Associates、App.com.pk | ⚠️ **必须回溯**，回溯后**降级为「解读」链接保留** |

> `humance-content-baseline` 的校对 CSV 里 `来源层级` 字段已有此分级，可直接当筛选器用。

### 12.3 三步回溯流程（缺一不可）

1. **读发文出处**：打开原引链接，看它引用了什么文号、有没有给原文链接。
   - 只写「MOHRE 发布了…」而**不给原文链接** → 判定为解读，必须回溯。
   - 给了原文链接 → 顺着打开，验证是否为官方域名。
2. **继续回溯**：目标 = 文号对应的官方发布处。常用路径
   - 部门官网新闻稿：`<部门域名>/en/media-center/news/<yyyy/mm/dd>/<slug>`
   - 政府门户引述页：`u.ae/en/information-and-services/...`（会在源处标 `*Text provided by MoHRE`）
   - 联邦立法门户原文：`uaelegislation.gov.ae/en/legislations/<id>`
3. **交叉核对**：把官方表述与原引逐项对齐（**日期 / 数值 / 阈值 / 时间表 / 废止关系**）。
   完全一致 → `✅ 内容一致·已换官方源`；有出入 → 按「现行 vs 拟更新」写进标注块，**正文数字不动**。

### 12.4 渲染形态（**链接两分法：站外只放官方原文，站内解读/工具自由加**）

2026-09-22 修订：Yoyo 拍板「解读可以留，但只能跳站内链接」+「可植入工具入口」。口径从
「单官方链接（删解读）」调回**三态混合**，但**站外一律只放官方原文**，站内的解读与工具必须指向品牌自有域名：

```
生效日期 2026-06-01（已正式生效） ｜ 来源：MoHRE（政府/官方门户） ｜ 官方原文 ↗ ｜ 解读：WPS 深度解读 ↗ ｜ 页面位置：薪酬支付
相关工具：🛠 合规自检 ↗  🛠 JD 生成 ↗
```

> ⚠️ 信息行里**不再有**「标注写入 / 校对ID」（2026-09-23 撤出，见 §2）；校对ID 改走块级 `data-cg-rid` 属性。


| 链接 | 位置 | 必须指向 | 缺省 |
|---|---|---|---|
| **官方原文 ↗** | 信息行 | 站外 **official**（政府/立法/部委门户） | 必填，无则被 L1 拦下 |
| **解读：… ↗** | 信息行 | 站内 **internal**（humancehr.com / anchorwe.com 的知识库·法规库·报告） | 可空，有则必须 internal（L6） |
| **相关工具 🛠** | 独立胶囊行 | 站内 **internal**（合规自检 / JD 生成 / 薪酬测算等） | 可空，有则每条必须 internal（L7） |

**站外只放官方原文**这一条刚性不变 —— 三方解析（律所/平台/媒体）无论「解读」还是「工具」都不准跳出去。
站内链接（我们的知识库、法规库、报告、工具）才是我们自己的价值沉淀，可放心加。无 `official_url` 时
**官方原文链接不渲染**（不退回渲染原引），并在上线前被 `qc_gate.py` 的 L1 拦下。

字段约定（批次配置 JSON）：

| 字段 | 含义 |
|---|---|
| `source` / `tier` | **升级后**的官方源名称 / 层级（`政府/官方门户`、`监管机构（央行/社保）`） |
| `official_url` / `official_name` | 一手源链接 / 一手源全称 —— **页面上唯一的站外链接** |
| `interpret_url` / `interpret_title` | 站内解读链接 / 解读标题（知识库·法规库·报告）；**必须是 internal 域名** |
| `tool_entries` | 工具入口数组：`[{label, url, tip}]`，每条 `url` **必须是 internal 域名**；建议 ≤2 个 |
| `orig_source` / `orig_tier` / `url` | **原引**名称 / 层级 / 链接 —— ⚠️ **仅供留档**（飞书台账「原引」列），**不渲染** |
| `trace` / `note` | 溯源状态 / 溯源说明（进飞书表） |

> `render_note()` 实现：**有 `official_url` → 渲染「官方原文 ↗」；有 `interpret_url` → 渲染「解读：… ↗」；
> 有 `tool_entries` → 渲染「相关工具」胶囊行**。无官方原文则连官方链接都不渲染（不退回渲染原引）。
> 站内链接不做降级出口：渲染层照常渲染，由 QC 的 L6/L7 兜底判 internal。

### 12.7 工具入口设计（2026-09-22 新增）

**一篇法规（一个标注块）放几个工具入口？—— 默认 1 个，跨领域最多 2 个，封顶 2 个（硬建议）。**

为什么是这个数：

- 标注块本质是「这条法规变了 + 官方依据」，信息密度已经不低。**工具入口是 CTA（行动召唤），不是信息**——多放只会稀释主信息。
- 每个标注块天然对应 **1 个最相关的工具**；只有当该法规横跨第二个明确领域时，才补第 2 个。放第 3 个就会显得「推销感」重、移动端胶囊折行难看。
- **全篇分布**：若 N 条全都挂同一个工具，用户会觉得重复。建议**按主题匹配**，让工具类型在篇内自然分散。

**主题 → 工具映射（推荐基准）**：

| 法规主题 | 首选工具 | 可补的第 2 个 |
|---|---|---|
| 合规/监管类（绝大多数法规） | 🛠 合规自检（Compass/合规哨兵） | — |
| 雇佣/招聘类（招聘导向薪酬、用工合规） | 合规自检 | 🛠 JD 生成（JD Studio） |
| 薪酬/社保/个税类 | 合规自检 | 🛠 薪酬测算器（如有） |
| 签证/工签类 | 合规自检 | 🛠 工签评估（如有） |

**渲染形态**：工具入口渲染为「相关工具：🛠 标签 ↗」胶囊行（站内主色描边 + 浅蓝底），与信息行用虚线分隔，区别于信息行的纯文字链接。每条 `url` 必为 internal 域名，QC 的 L7 强制、L8 对 >2 个告警。

`tool_entries` 字段约定（批次配置 JSON）：

```json
"tool_entries": [
  {"label": "合规自检", "url": "https://humancehr.com/compass", "tip": "一键核查本条合规"},
  {"label": "JD 生成", "url": "https://anchorwe.com/jd", "tip": "生成岗位 JD"}

```

## 十三、左侧目录「小气泡数字」★（2026-09-22 落地，踩了四个坑）

### 13.1 需求

页头版本条 / 章节标题徽标都只能表达「**当前这一章**有多少更新」。用户在阅读任意一章时，看不到其余章节的更新情况 —— 需要让**左侧目录**（12 章导航）也带上数字气泡，一眼看出哪几章有更新。

### 13.2 为什么 DOM 改不了（读前端源码确认）

前端 `TableOfContents` 组件（`/assets/TableOfContents.C_Npw-3T.js`）的 props **只有 `content` 与 `className`**，它把整篇 content 当**字符串**收进去，自己扫章节：

```js
const e = /<h2[^>]*>([\s\S]*?)<\/h2>/gi;
for (; (i = e.exec(o)) !== null; ) {
  const h = i[1].replace(/<[^>]*>/g, "").trim();   // ← 剥掉所有标签，只留纯文本
  r.push({ id: `heading-${d}`, text: h });          // ← d 从 0 全局递增
}
// 渲染：children: [t.text, " ", isCurrent]  —— 没有 data 属性、没有插槽、没有状态字段
```

三条由此封死的路：

| 想法 | 为什么不行 |
|---|---|
| 往 h2 里塞 `<span class="bubble">2</span>` | `replace(/<[^>]*>/g,"")` 把标签剥光，目录里只会多出一串裸文本「薪酬支付2」 |
| 复用 h2 上的 `::after` 徽标 | 伪元素不进 `textContent`，目录天然看不见 |
| 传状态给 TOC 组件 | props 只有 `content`/`className`，没有口子 |
| 改 h2 文本带数字 | **更糟**：前端用 h2 文本做章节名匹配（`a === decodeURIComponent(pathname)`），塞数字会让章节匹配直接失配 |

⇒ 唯一挂载点：**CSS 选择器 `a[href="#heading-N"]` 的伪元素**。content 里注入的 `<style>` 在页面上是全局生效的（章节徽标即证据）。

### 13.3 四个坑

**坑 1 · 序号口径和 content-section 序号是两套**
`N` 是「content 里**所有** h2」的全局序号（前端正则不限 `class="section-title"`，且空标题不占号），不是 content-section 序号。当前 12/12 恰好相等，但规则不同 → 用 `toc_index_map()` 严格复刻，别图省事用 `_sec_idx`。

**坑 2 · 挂 `::after` 会把气泡挤到第二行**
侧栏宽 `md:w-[160px] lg:w-[180px]`，最长项「外企本地化与签证管理」约 140px，加气泡后放不下。`::after` 的源流位置在文本**之后** → float 被推到第二行、悬在文字下方（实测截图确认，很难看）。
→ 改挂 **`::before`**：它在文本**之前**，float 先占第一行右侧，文本自动避让 → 气泡永远锁在第一行右侧，长标题只让文本折行。

**坑 3 ★ · 平台会给 `<style>` 自动加 `.article-isolate` 作用域前缀**
平台（PostCSS 作用域插件）把 `.table-of-contents a[href=...]::before{…}` 改写成
`.article-isolate .table-of-contents a[href=...]::before{…}`。
而左侧目录挂在 `<aside id="toc-container">` 里、在 `.article-isolate` 容器**外面**
⇒ 前缀一加，选择器**永远命不中**，线上表现是「样式块明明在、气泡一个都不出现」（第一版就是这样，白落一次）。

逃逸规律（用不存在的选择器做零影响探测，全部实测）：

| 写法 | 是否被加前缀 |
|---|---|
| `.zz{}` 类开头 | ❌ 加（且**加 3 次**） |
| `nav.zz{}` / `li a{}` / `body nav{}` 元素开头 | ❌ 加 |
| `[href="…"]{}` 属性开头 / `*{}` 通配开头 | ❌ 加 |
| `:root nav{}` | ❌ 加（且选择器被吃成 `.article-isolate {}`） |
| `@media` / `@layer` / `@supports` **块内** | ❌ 照样递归加 |
| `@scope (.x){ a{} }` —— **块内元素选择器开头** | ✅ **原样放行** |
| `@scope (.x){ .inner{} }` —— 块内类开头 | ❌ 加 |

⇒ **唯一可行写法**：整块包 `@scope (.table-of-contents){…}`，内部只用元素选择器 `a[href="#heading-N"]::before`。
顺带好处：作用域根把规则限制在目录内，`.article-isolate` 里若有同名锚点也不会误伤。

**坑 4 · 这个 `<style>` 必须每章注入一份**
它虽然作用于页面骨架，但页面**按章渲染**（规范 §11）—— 缺了哪一章，打开那一章的页面时目录就一个气泡都没有。

### 13.4 最终产物

```html
<style>
@scope (.table-of-contents){
a[href="#heading-2"]::before{content:"2";float:right;margin:2px 0 0 6px;min-width:16px;height:16px;
  line-height:14px;padding:0 4px;border-radius:999px;font-size:10px;font-weight:700;font-style:normal;
  text-align:center;box-sizing:border-box;background:#fef3c7;color:#b45309;border:1px solid #fcd34d;}
…
}
</style>
```

- 数字 = 该章本次标注**总项数**；颜色 = 最高优先级状态（`pending > check > keep`），配色复用 `STATE`（与章节徽标同源）
- 16px 圆 + 10px 字：1 位数字正方形，2 位数字自然拉成胶囊
- 无更新的章节不生成规则 ⇒ 目录上零干扰
- 浏览器兼容：`@scope` 需 Chrome 118+ / Safari 17.4+ / Firefox 128+；不支持时整块被忽略，**优雅降级**（无气泡，不影响任何既有内容）

## 十四、一次校验 · 上线前 QC 流程 ★（2026-09-22 建，2026-09-24 扩到 31 项 · 含内容质量 CQ 组 + 申报式正文修复 BF 组）

### 14.1 为什么单独立一道闸门

前面 14 项门禁（§4 / §6 / §13）验的都是**形态**：HTML 长对了、元素在正确位置、颜色对、字号对、气泡渲染出来了。
它们**证明不了四件事**：① 标注块里的链接到底是不是官方的；② **官方外链到底打不打得开**；
③ 写进页面的文字本身有没有问题（说明文本过时、字段缺失、重复注入）；④ 文案是不是**客户向**的
（内部过程时间 / 内部字段有没有漏进客户视野）。

所以把「内容正确性 + 前端可渲染性 + 客户向文案」独立成一道 QC，**位置固定在落线之前**：

```
build（形态门禁）→ verify_render（真渲染）→ qc_gate（一次校验：内容 + 链接 + 外链可达 + 渲染 + 生效 + 客户向文案）
   → 暂存 + 通知 → 人工确认 → release_gate（P 组）→ release_apply（写线上）
   → verify_secondary --source live（三次校验）      ↑ 独立可跑，退出码 0/1
```

`release_stage.py` 内部**强制**串接 qc_gate 与 verify_secondary，未通过不允许进入暂存；
`release_apply.py` 内部**强制**串接 release_gate，未通过整批拒绝写入；流程固定为
**先构建全部国家 → 跑齐校验 → 通知待确认 → 人工确认 → 才逐国 PUT**，杜绝「一半写了一半点好」的脏状态。
（应急/回滚仍可用 `batch_guide_patch.py --apply --legacy` / `--restore`。）

### 14.3 三个实现要点（踩过）

1. **T5 别用 `</s(?!tyle)` 这种写法判「半截标签」** —— 它会把 `</span>`/`</strong>` 全算成截断（实测误报 479 处）。
   正确写法 `</(?!\w+\s*>)`；并且要判**新增量**（`after` 与 `before` 的差值），因为原文自带
   `<contact-qrcode style="display:none">` 这类自定义元素。
2. **T1「正文零改动」要独立实现摘除逻辑**，不复用 `build()` 的 `inserted` 列表（QC 是可独立跑的工序，
   不该依赖构建期的内存状态）。摘除清单 = 标注块 + 版本条 + `<style>` + `data-cg-badge`/`data-cg-state`，
   **改 `build()` 的注入清单必须同步改这里**。
3. **T8 是这次真正抓到东西的一项**：`trace` 字段写着「✅ 内容一致·已换官方源」，
   而 extra 里还留着「未取得 GPSSA 官方原文」——溯源完成后忘了改文案。
   正则：`(未|尚未|没有|未能)取得[^。；]{0,16}官方|(须|需|待)以[^。；]{0,16}官方[^。；]{0,8}(核实|确认)`。
   ⚠️ 只匹配**指向来源**的表述 —— 「表内数字待核对」这类指向内容的说法不能误伤。
4. **外链门禁必须"能离线跑"**：QC 加了 `--link-mode live|cache|off`（默认 `live`）。
   `live` 会真的发请求，跑得慢、还受本机网络影响；所以**发布链路上用 `cache`**
   （`release_stage.py` 就是这么调的，读 `_link_check.json` 缓存），**人在本地排查时用 `live`**，
   完全不想等就 `off`。缓存带 `_inherit()` 继承规则：上次验真为「可打开」的、30 天内不会被后来的网络抖动翻掉
   （`dead` 除外，死链永远优先）。详见 **§19**。

> ⚠️ **A 类用例必须自查「篡改真的生效了吗」**（2026-09-23 踩坑）：
> 用例的锚点是产物里的**字面量**，产物文案一改（如版本条去掉「校对批次」），
> `str.replace` 就**静默变成空操作** —— 产物没被破坏 ⇒ 门禁当然不拦 ⇒ 用例报"漏放"
> （N4「校验时间」就是这么暴露的）；而更危险的是**若某条期望「不拦」，空操作会变成假通过**

## 十五、前端脆弱 walker ★★（2026-09-23 线上事故换来，本技能最贵的一条约束）

### 15.1 事故现场

阿联酋指南线上 **12 章只剩前 4 章**能显示；`个税` / `福利` / `休假政策` / `合同管理` / `员工入职` /
`员工离职` / `解雇与争议处理` / `外企本地化与签证管理` 全部弹出：

> 错误信息　无法加载内容。h2Content为空。　尝试提取的h2标题：个税

而 `content` 字段本身**一条没丢**（12 个 `content-section`、6 条标注、114,619 字符全在）。
⇒ 不是数据问题，是**前端渲染时找不到章节**。同站其他国别（无标注）12 章全正常 ⇒ 只有注入过的国家中招。

### 15.2 根因：前端用朴素字符串计数，且推进逻辑越位 1 个字符

前端 `ContentUpdater` 组件切分章节时**不是 HTML 解析器**，而是朴素 `indexOf` 计数：

```js
f = 1; u = g + 1;
while (u < n.length && f > 0) {
  v = n.indexOf("<div",   u);
  d = n.indexOf("</div>", u);          // 6 个字符
  if (d === -1) break;
  if (v !== -1 && v < d) { f++; u = v + 4; }
  else {
    f--;
    if (f === 0) { /* 找到块 */ t = d + 7; break; }   // ← d+7 越过 1 个字符
    u = d + 7;                                        // ← 同样越位
  }
}
if (f > 0) break;                       // ← 一章错位，后面全灭
```

`"</div>"` 只有 **6** 个字符，但两处推进都写 `d + 7` ⇒ **每次越过 1 个字符**。
后果：当 `</div>` 后面**紧贴**下一个标签时（`</div><div` 或 `</div></div>`，中间**没有任何字符**），
紧贴的那个标签正好落在被越过的那个字符上，**被整条跳过**：

- 跳过的是一个 `<div` ⇒ 少算一次「开」⇒ 深度 `f` 偏低 ⇒ 顶层块**提前闭合** ⇒ 后续章节全被吞掉
- 跳过的是一个 `</div>` ⇒ 少算一次「闭」⇒ 块**延长**并吞掉下一个兄弟节点

我们注入的标注块当时是多层 `<div>` 拼的，行与行之间正好 `</div><div` 紧贴 ⇒ 触发条件全中。
实测：`content_AFTER.html` 里 `</div><` 邻接共 **9 处，全部落在 6 个标注块内部**（`</div><div` × 3 + `</div></div>` × 6）；
基线 `content_ORIGINAL.html` 该邻接数 = **0**。复刻算法结果：**基线 13 块 / 注入后只剩 4 块**。

### 15.3 修复：结构性免疫（不是靠补空白）

两条硬约束，写进 `guide_patch_lib.py`：

```python
WALK_UNSAFE = re.compile(r"</div><")
def harden(html):   return WALK_UNSAFE.sub("</div>\n<", html)   # 兜底：邻接处补换行
```

1. **注入片段内不得出现 `</div><`** —— `harden()` 对每个渲染输出兜底补换行，`validate()` / `qc_gate.py` R1 双重阻断
2. ★ **标注块内部一律不用 `<div>`**，改用 `<p>` / `<span>` / `<strong>` / `<a>`
   ⇒ 整个标注块对前端 walker 只呈现 **1 开 1 闭** 的 div，**即使标签之间一个字符都不剩也不会失衡**

> 为什么坚持用方案 2 而不是只补空白：本技能实测过**平台会折叠纯空白行**
> （线上存的 `</div>\n  \n  <div` 被压成 `</div>\n  <div`，6 条块共少 18 字节）。
> 只补空白能过，但它依赖「平台保留空白」这个**未承诺行为**；结构化才是一次到位的解法。

### 15.4 判据与门禁

`frontend_blocks(content)`（**刻意复刻前端朴素 indexOf 实现**）返回的章节数 == 指南应有章节数。

> ⚠️ 与 `_top_level_divs()`（正则 + 配平，正确解析）是**两套**东西，别混用。
> 2026-09-23 之前只用正则版做「前端分章模拟」，所以 **本地全绿、线上全空**。这是本次最大的教训。

新增门禁（已并入 `qc_gate.py`，随 §18 的 F 组与 §19 的外链组一并扩到 **24** 项）：**R1 无 `</div><` 邻接** / **R2 复刻 walker 必须发现全部章节**。

## 十六、二次/三次校验 · 全文校验 ★（2026-09-23 建，2026-09-23 同日扩为「三次校验」口径）

### 16.1 为什么还要第二道闸门

一次校验（§14）校验的是**本地产物**（`content_AFTER.html`）——它只能证明「**我打算写的**没问题」，
证明不了「**整篇正文渲染出来**没问题」。2026-09-23 事故正是钻了这个空子：
本地产物静态校验全绿、真渲染也全绿，**线上却是坏的**（因为前端 bug 只在真实 walker 下暴露）。

所以 `verify_secondary.py` 用**同一套 S1–S18b**，在三个时点各跑一次：

```
build → qc_gate（一次校验 · 落线前 31 项）
   → verify_secondary --source staging（二次校验 · 全文校验 · 暂存稿 S1–S18b）
   → 暂存 + 通知 → 人工确认 → release_gate（P 组 7 项）→ release_apply（写线上）
   → verify_secondary --source live（三次校验 · 全文校验 · 线上回读 S1–S18b）
        ↑ 校验对象 = Strapi 回读的 content → 台账回写「三次校验*」
```

| 次序 | 名称 | 被校验对象 | 台账字段 |
|:-:|---|---|---|
| 1 | **一次校验** · 上线前 QC | 本地产物 | `QC 状态` |
| 2 | **二次校验** · 全文校验 | **本地暂存稿**（`content_AFTER.html`） | `二次校验结果 / 时间 / 说明` |
| 3 | **三次校验** · 全文校验 | **Strapi 回读的线上 content** | `三次校验结果 / 时间 / 说明` |

> 2026-09-23 Yoyo 定的纪律：**全文校验必须在落线前就能跑**，所以 `verify_secondary.py`
> 加了 `--source staging`（见 §17.2）——**先过校验、再上线**，而不是"先上车后补票"。
> 同一次会话中 Yoyo 又把口径明确为「**阶段 C 算三次校验**」——两次跑同一套 S 项，但各记一组台账字段，互不覆盖。

## 十七、两阶段发布与发布确认门禁（P 组）★ 2026-09-23 建

### 17.1 需求与设计

Yoyo 原话：「补充一个门禁及正式发布通知，**二次校验全文（内容质量及门禁）通过后，再正式上到线上，
通过前先存本地**，通过助手提示我的微信，那篇国别指南、对应链接、全文校验结果，
**待上线，同我确认，是否正式上线**。」

三条被写进流程的纪律：

1. **先校验、再上线**（不是"上线后补验"）；
2. **通过前先存本地** —— 校验通过前，产物只落磁盘，线上零改动；
3. **人工确认是硬闸门** —— 门禁全过 ≠ 可以上线。

```
阶段一 release_stage.py
  ① build（本地，绝不 PUT）
  ② qc_gate.py                            31 项   ← 一次校验（含官方外链可达 · 内容质量 CQ · 申报修复 BF · --link-mode cache）
  ③ verify_secondary.py --source staging  S1–S18b ← 二次校验：对**暂存稿**做整篇校验
  ④ 写 _release/pending_release.json（含每国 sha / 链接 / 校验摘要 / 有效期）
     + notify_channels.py 推四要素通知
     ⚠️ 若 ② 的 L9 挂起（有待人工点验的外链），另写 _release/_link_todo.md 并在通知里列出点验清单
阶段二 release_apply.py --approve <all|slugs>
  ⑤ release_gate.py（P1–P7）→ 不过直接拒
  ⑥ 只 PUT 暂存产物（不重新构建）；PUT 前再核 sha
  ⑦ 回读复验（L.push_and_verify）+ 回写台账
  ⑧ 事后必跑 verify_secondary.py --source live --sync-ledger   ← 三次校验
```

> 阶段一的 ② 会**读缓存**（`--link-mode cache`）而不是现场逐条发请求 —— 外链的现场探测在构建当天已经做过一次，
> 发布链路再探一遍只会让发布变慢、还可能因网络抖动把好好的链接判成可疑，然后在最不该卡的地方卡住。


### 17.2 `staging` 模式下 S8 换语义（关键设计）

`verify_secondary.py` 的 S8 在两种模式下判**不同**的事：

| 模式 | S8 判什么 | 为什么 |
|---|---|---|
| `--source live`（三次校验） | 线上 == 本地产物（剥 `<style>` 等价） | 防"本地改了但没落线 / 落错版本" |
| `--source staging`（二次校验） | **线上正文（摘除我方注入物后）== 本轮基线（未被他人改动）** | 落线前的真实风险是**基线被别人改过**，一上线就把别人的改动覆盖掉 |

> ⚠️ **必须两边都先 `strip_injections()` 再比**。原因：改版重发（文档已上线过）时，
> 线上 = 干净正文 + 我们**上一版的注入物**，与干净基线**天然不等**。
> 若直接比 raw，会对所有"改版重发"场景**误判为基线漂移**。
> 判定口径：
> - 首次落线：线上还是干净正文 ⇒ 天然相等
> - 改版重发：线上摘掉注入物后 == 干净基线 ⇒ 仍相等，可以安全落线
> - 真被他人改过正文 ⇒ 不相等 ⇒ 拦下，提示 `--refresh` 重取基线
>
> 实测（2026-09-23 阿联酋）：文档已上线过，`strip_injections(线上) == 基线` 为 **True** ⇒ S8 放行；
> 而早期用 raw 比对时显示 `线上 115214 vs 基线 81696` 被拦 —— **误报**，已修成上述口径。

## 十九、官方外链可达性校验 ★★ 2026-09-23 建（Yoyo：「上线前 qc 要校验下官方外链，是能打开的」）

### 19.1 为什么单独做一件事

在 §19 之前，QC 的所有链接门禁（L1–L4）验的都是**链接长什么样**：有没有、是不是官方域名、数量和条数对不对。
**没有一项验它到底打不打得开。** 而链接打不开恰恰是客户最容易发现、也最难解释的错误 ——
页面写着「来源：MoHRE 官方原文 ↗」，点进去 404，整条标注的可信度就归零了。

> 定位一句话：**L1–L4 管"像不像"，L5/L9 管"通不通"。**

### 19.2 唯一实现 = `scripts/link_check.py`

**所有**外链判定都必须走这个模块（渲染层、QC、全文校验、发布链路、台账回写），不许任何脚本自己写 `urllib` 探一遍。

| 能力 | 说明 |
|---|---|
| **五分类判定** | `ok` 可打开 ／ `blocked` 被站点拦截（403/401 等）／ `dead` 死链（4xx，排除 401/403/429）／ `server_error` 站点故障（5xx）／ `unreachable` 本机不可达（DNS/超时/代理） |
| **重试** | 默认 `tries=3`（`--tries` 可调），取**多次采样中的最好结果**；官方站常偶发抖动，单次采样不可信 |
| **响应体校验（两层）** ★ | 不只比状态码。`_sniff()` 读 2048 字节正文，返回四态 —— `ok` 可信 ／ `proxy` 代理/网关错误页 ／ **`waf` 站点拦截页** ／ **`gone` 内容不存在**；再由 `classify_response()` 归一成分类。**状态码不可信时，正文是最后判据** |
| **标题级识别** ★ | WAF 与"404 渲染成 200"都靠**页面标题**识别（`WAF_TITLE` / `GONE_TITLE`）。只认标题不认正文关键词 —— 正文里出现 `access denied` 的合法页面太多，认正文会误伤（E3 用例专门守这条） |
| **缓存格式版本** ★ | `CACHE_VERSION`：**分类算法改了就 +1**，老缓存一律作废。否则被老算法误判的结论会被 `_inherit` 继续继承（踩过：WAF 拒绝页被判 ok 写进缓存，改完算法仍被"继承"保留 ⇒ 假放行长期存活） |
| **并发** | `ThreadPoolExecutor`，默认 5 并发（`--workers`） |
| **缓存** | 结果落 `_link_check.json`，`--link-mode cache` 时不再发请求 |
| **继承** | `_inherit()`：上次验真 ok 且未过期（`OK_TTL_DAYS = 30`）⇒ 本次网络抖动不推翻它；**`dead` 永远优先**，绝不继承；**历史结论的 `sniff` 命中拦截页特征也不继承**（那条 ok 本身就是误判） |
| **人工背书** | `--mark-verified` 把「人工已点验」写进批次配置（`notes[*].link_verified`），机器结果不得覆盖人的结论 |
| **两种抽取源** | `collect_from_config()` 从配置抽（含 `official_url` / `interpret_url` / `tool_entries`）；`collect_from_html()` 从**产物 HTML** 按 `data-cg-rid` 抽 |
| **URL 去重** | `_dedupe_pairs()`：`--config` 与 `--html` 同给时两者覆盖同一批链接，不去重会把 6 条当 12 条（汇总翻倍、缓存重复）。去重后每条 URL 只探一次，对官方站也更友好 |

### 19.3 判定 → 门禁 → 台账（三段链路）

| 判定 | 含义 | QC 门禁 | 台账「外链状态」写法 |
|---|---|---|---|
| `ok` | 机器验证可打开 | 放行 | `✅ 可打开（HTTP 200 «<页面标题>»）` |
| — | **人工已点验** | 放行（**优先级最高**） | `✅ 可打开（人工点验 · <人> @ <日期>）` |
| `dead` | 死链（4xx） | **L5 阻断** | `❌ 死链（HTTP 404）` |
| `blocked` | 站点反爬拦截 | **L9 阻断**，除非有 `link_verified` | `⚠️ 需人工点验（站点拦截自动化）（HTTP 403）` |
| `server_error` | 站点故障 | **L9 阻断**，同上 | `⚠️ 需人工点验（站点故障）（HTTP 502）` |
| `unreachable` | 本机不可达 | **L9 阻断**，同上 | `⚠️ 需人工点验（本机不可达）（Tunnel connection failed: 502 Bad Gateway）` |

**取值优先级：人工背书 > 机器验真（ok）> 机器判定。** 实现见 `ledger_text(res, human=None)`。

> **为什么 `dead` 直接拦、其余走人工**：死链是**确定的事实**（4xx 是站点在明确说「没有这个页」），
> 机器可以直接下结论；而「403 被反爬」「本机连不上代理」都是**观测到我方侧的问题**，
> 不能反推链接有问题。让机器在这里硬判，就是让**环境的不确定性**去决定**内容能不能上线**。

> **纪律：不许代替别人填背书。** `--mark-verified` 只能由**真的动手点开过链接的那个人**执行。
> 巴蒂自己抓取通道取到了正文，可以写 `by:"巴蒂"` 并在 note 里说清凭据；但**必须同时写明「待 Yoyo 浏览器复核」**，
> 让复核责任显式留在人身上 —— 而不是把「巴蒂猜的」包装成「验证过的」。

> ⚠️ **判 `ok` 的门槛比"状态码 200"高得多**（2026-09-23 加固）：必须同时满足
> ① 状态码 2xx/3xx ② 响应体非空 ③ **页面标题不是代理错误页、站点拦截页、或"内容不存在"页**
> （`SUSPECT_BODY` / `WAF_TITLE` / `GONE_TITLE`）。
> 少任何一条都不算 ok —— 因为「✅ 可打开」这个结论会**写进台账并给客户看**，假放行的代价比"多一次人工点验"高得多。
> 两个真实反例见 §19.5 的坑 1 和坑 2。

### 19.4 实测：这个门禁真的抓到了一条死活链

**背景**：PR-048（阿联酋 Emiratisation 罚则）的 `official_url` 指向 `u.ae` 一个页面。
在本文档 §19 建立之前，它一路通过 L1–L4（域名是官方的 `.ae`、数量对、是官方原文链接）——
**没有任何门禁能发现它打不开。**

**证据**：

| 样本 | 成功 | 状态 | 落点 |
|---|:-:|---|---|
| 原链接 `…/jobs/**Sector**-of-employment/…/emiratis-employment-in-the-private-sector` | **0/8** | IIS 返回 `Location: /en/error/404` | 404 页 |
| 规范链接 `…/jobs/**sector**-of-employment/…/emiratis-employment-in-private-sector` | **8/8** | 200，标题「Employing Emiratis in the private sector」 | 正文含 2026 年 AED 9,000/月 罚则 |

**结论**：两处差异（`Sector` 大写首字母 + 末段拼写）是**同一个官方页的规范化形式**，
正文里 2026 年罚则金额与 PR-048 的拟更新值一致 ⇒ **这不是「来源变了」，是原本就贴错了 URL**。
修法是直接在批次配置里改 `official_url`，并在 `trace` 里留下 8/8 vs 0/8 的证据（不只是写「已修正」）。

> **这条案子的价值不在修好一个链接，而在它证明了**：只验「像不像官方」的门禁，
> 可以让一个 404 链接在页面存活很久而无人发现。**外链可达性必须成为上线前的独立门禁。**

### 19.5 代理环境下的坑（本机实测）

本机出口是 MITM 代理，这带来三个必须写进代码的坑：

1. **代理会返回「假 200」** ★ —— 探测 `u.ae` 死链时，8 次采样里有 **1 次**返回 200，
   而且返回的页面标题竟是**正确页面的标题**。如果只看状态码，这条死链会被判成 ok。
   ⇒ 这就是 `_sniff()` **响应体校验**存在的原因：状态码不可信时，正文是最后一道判据。

2. **站点自己也会返回「假 200」** ★★（比第 1 条更隐蔽，因为**不是代理的锅**）——
   `gpssa.gov.ae` 某条链接返回 **HTTP 200**，响应体却是站点 WAF 的拒绝页：
   `<title>Request Rejected</title>`，正文只有一句 "The requested URL was rejected…"。
   状态码 200 + 正文非空 ⇒ 第一版 `_sniff()` 判它"可信" ⇒ **判成 ✅ 可打开、写进台账**。
   **这是假放行**：台账写着「可打开」，客户点开是拒绝页 —— 比漏拦更糟，因为它把错误变成了"已核实"。
   ⇒ 修复：`_sniff()` 升级为**四态**（ok / proxy / waf / gone），识别的关键是**页面标题**。
   ⇒ **教训**：`非空正文` 不等于 `正确正文`。凡「验真」，都要问一句"我看到的是**谁的**页面"。

3. **同一 URL 的结果会飘** —— `gpssa` 在 200 与连接失败之间摆动，`uaelegislation` 稳定返回 403
   （脚本 UA 被反爬挡，但独立抓取通道取到了完整正文：Federal Decree-Law No. 33 of 2021，Active，生效 2022-02-02）。
   ⇒ 这是 `_inherit()` 存在的原因：**已经验真的结论不该被后来的网络抖动推翻**，
   否则每次跑 QC，「需人工点验」的列表都在变，人工点验永远做不完。
   ⇒ 但继承必须**只继承可信的 ok** —— 历史 `sniff` 命中拦截页特征的不继承，否则错误会被"继承"成长期事实。

> ⚠️ 因此**负向测试不能用真实探测**（§14.4 C 组）：用不确定的输入去测确定的门禁，结论不可信。
> 正解是把判定结果做成**夹具**（改写 `_link_check.json` 缓存），只测门禁逻辑本身。
> 而**分类器本身**要用**合成响应体**单测（§14.4 E 组）—— 因为"代理恰好返回 WAF 页"这种输入没法按需复现。

### 20.1 为什么单独立一个维度

前六组门禁（G/L/T/R/E/F）都只看**我方注入物**：标注块长对了、链接对、文案对、不污染正文。
但 Yoyo 圈出的三张截图里，问题**不在标注块**上 —— 是**正文本身**：

| 截图 | 现象 | 归属 |
|---|---|---|
| 核心数据概览卡片 | 数值字号大得压过页面章节标题 | **排版** |
| 福利章节首图 | 图片是 AI 生成的中文乱码 | **配图** |
| 标注块状态 | 「✅ 已核实维持」读着别扭 | 客户向文案（已并入 F3 + `STATUS_TEXT`） |

⇒ 门禁必须往**全文**扩一层。这是本项目第一条「看整篇正文」的检查 —— 也因此**必然查出历史存量问题**，
所以它必须配套「已知缺陷基线」机制（§20.4），否则要么永久阻断、要么装看不见。

### 20.2 两条通道，各自保留真值

唯一实现 = `scripts/content_quality.py`。两条通道**不能合并**，因为它们回答不同的问题：

**① 静态通道 `scan_html(html)`** —— 查配图**来源层**（不渲染，快、可全站跑）

| 编号 | 检查 | 级别 |
|:-:|---|:-:|
| CI1 | 空 `src` / 缺 `src` | block |
| CI2 | `data:` base64 内联图（撑爆 `content`，平台侧不可维护） | block |
| CI3 | 相对路径（`/images/x.png`）—— 平台渲染时基准路径不确定 | block |
| CI4 | 占位图（`placeholder` / `example.com` / `via.placeholder` / `lorempixel` / `fakeimg` …） | block |
| CI5 | 托管在**非自有域**（图床） | **warn** |
| CI6 | `alt` 敷衍（空 / 长度越界 / 「图片」「image」「截图」类） | warn |
| CI7 | 图片**打不开**（复用 `link_check.py`，DNS 预检 + 响应体 sniff） | block |

**② 渲染通道 `render_check()` + `judge()`** —— 查排版**呈现真值**（无头 Chrome 取 computed style）

| 编号 | 检查 | 级别 |
|:-:|---|:-:|
| CT1 | 字号**超出上限**（`> max_font_px`） | block |
| CT2 | 横向溢出（`scrollWidth > clientWidth`） | block |
| CT3 | 同组卡片高度**极差**超限 | block |
| CT4 | 字号**低于可读下限**（`< min_fs`） | block |
| CI8 | 渲染后**破图**（`naturalWidth === 0`） | block |
| CI9 | 图片被放大发虚（`w > nw × 1.15`） | warn |
| **CQ9** | 渲染目标里**没有 `.content-section`** ⇒ **fail-closed 报错** | block |

> **为什么两条都要**：CI7 能发现「URL 打不开」，但发现不了「浏览器怎么都渲染不出来」（CI8）；
> CT1 能发现「box-sizing 把卡片撑破」，但静态 HTML 里根本看不到字号。**两边都不是另一边的超集。**

### 20.3 阈值与理由（唯一真相源 = `references/image-hosts.json` 的 `_render_policy`）

```json
{"max_font_px": 24, "min_font_px": 12, "card_height_tol_px": 40, "upscale_ratio": 1.15}
```

`max_font_px = 24` 不是拍的，是**从本页自己的层级推出来的**：

| 层级 | 字号 |
|---|:-:|
| 正文 | 14px |
| 二级标题（subsection） | 18px |
| 章节标题（`.section-title`） | **22px** |
| **门禁上限** | **24px** |

⇒ 正文区域里出现 >24px 的值，意味着它**比本章一级标题还大** —— 读者会把它当成整篇的重点，这就是 Yoyo 说的「大得离谱，不太和谐」。

> ⚠️ 阈值必须**参数化**（`render_findings(d, thr=...)`），且**判定不许写进 JS 探针**。
> 探针只负责**采集原始读数**（`{px, tag, cls, head, text}`），判定集中在 Python 的 `judge()` ——
> 这样改阈值 / 加豁免后**重算即可生效**，不用重渲染。

### 20.4 已知缺陷基线（豁免单）—— 降级 + 留痕 + 派单，不是垃圾桶

`references/quality-baseline.json`，本期两条：

| id | rule | 问题 | 影响面 | 责任方 |
|:-:|:-:|---|---|---|
| `KB-001` | CT1 | 统计卡片数值 **26.4px** 高于本页章节标题 22px（层级倒置） | 全站 **76** 国 · **2623** 张卡片 | 前端 / `anchorai blue.css` |
| `KB-002` | CT3 | 同组卡片高度不齐（长数值折行撑高） | 全站；实测 UAE 组 211/211/211/255px，极差 44px | 前端 / `anchorai blue.css` |

**为什么必须有这个机制**：`KB-001` 的根因**不在正文里**，而在外站样式表
`https://dev-gpt.anchorwe.com/anchorai/css/blue.css` 的 `.stat-value{font-size:1.65rem}`。
我方（内容运营）**改不了**它，但它会让全站 76 国永久阻断 —— 门禁就从**把关**退化成**停摆**。

三条路只有第三条对：

| 做法 | 结果 |
|---|---|
| 照旧阻断 | 76 国永远发不出去，门禁变成路障 |
| 静默放过 | 等于装看不见，缺陷永远不修 |
| **降级 + 留痕 + 派单** ✅ | 本批能发（历史问题不背在自己身上）；但**报告里看得见**、**台账里有责任方和修法**、**修完删条目**即恢复阻断 |

**硬性约束**：每条豁免必须写清 `rule / match_cls / scope / root_cause / owner / found_at / fix` 七项（缺一项不许进）。
`match_cls` 是**收窄命中范围**的关键 —— `KB-001` 的 `match_cls: "stat-value"` 意味着**只有 `.stat-value` 这一个类名**被降级。

⇒ **基线之外的同类命中依然阻断**（换类名 / 本文自己引入的新字号问题），这条由 `selftest_gates.py` 的 **F3** 用例守住：
「`promo-badge` 30px 喂真实豁免单 → 必须仍 `block` 且无 `known`」。

> **判据**：`「我想让某个新问题被放过，要动几个文件？」` —— 必须 ≥2（改 `quality-baseline.json` + 报告里出现），
> 且新条目会**永久留在文件里**（有 owner、有 found_at）。**让放过一件事变得麻烦，就是这道机制的全部意义。**

### 20.5 缓存设计：只存原始读数，判定每次重算 ★

```python
RENDER_CACHE_VERSION = 2            # 判定算法一改就 +1
def load_render_cache(path):        # 校验 ver + 阈值指纹，不符即丢弃
def save_render_cache(path, pages)  # pages[u] = raw probe output（不是 findings！）
```

**为什么**：判定口径（阈值、豁免单）会演进，而缓存会被跨天复用。
若把 `findings` 写进缓存，就会出现「**改了规则但老缓存还在按老结论判**」——
改严了不生效（假通过）、加豁免了不降级（假拦截）。这与 `link_check.CACHE_VERSION` 是**同一类 bug**（§19.5 坑 3）。

实测踩过：加 `quality-baseline.json` 后，S16 仍报「排版阻断 34 条」，因为缓存里存的是**判定结果**。
改成「缓存只存 raw、读时 `judge()` 重算」后，立刻变成「已知缺陷（已派单，降级告警）34 条 · 排版阻断 0」。

### 20.8 复盘：三条收获

1. **门禁范围要跟着「客户的感受」走，而不是跟着「我们的动作」走。**
   前六组都在验「我注入的东西对不对」；Yoyo 的三张截图证明，**客户看到的整篇正文才是产品**。
2. **历史存量问题必须有第三条路。** 「阻断」会停摆，「放过」会装瞎 —— 只有「降级 + 派单 + 报告里看得见」能让门禁持续运转又不失守。
   但降级必须是**定向**的（`match_cls`），且**基线之外的同类命中照样拦**（F3 用例守着）。
3. **缓存不能存判定结果。** 存了就等于把「当时的规则」固化成事实 —— 改规则改不动（§20.5）。
   凡是有「阈值 / 豁免 / 分类算法」的缓存，都必须**只存输入、读时重算**。

### 20.9 普查顺带发现的两个隐藏缺陷（不属本次范围，但必须留痕）

**① 生产页面加载 `dev-gpt` 域的样式表** —— UAE 薪酬支付页的实际 CSS 来自
`https://dev-gpt.anchorwe.com/anchorai/css/blue.css`（**dev 环境域名**）。
开发域一旦下线或被改，全站样式会同时崩。**建议前端确认这是否是有意为之。**

**② 两个国别指南的 slug 被拼接了** —— Strapi 里：
`china-taiwan-country-guideqatar-country-guide`、`cyprus-country-guide-oman-country-guide`。

> 另外，台湾福利章的首图是 **AI 生成的中文乱码**（「丝具梓吝痳夔觅体展示」…，托管在 `s.coze.cn`）——

> ⇒ 记录在案，但**不纳入自动门禁**：自动门禁判「能不能显示」，判不了「显示得对不对」。

## 二十一、申报式正文修复 ★★ 2026-09-24 建

> 起因：阿联酋「劳动法规」章首图的 URL **域名被写错**（`s.cocecdn.net` 这个域名不存在 ⇒ DNS NXDOMAIN），
> 客户打开页面看到的是裂图；同一个短链 id 在正确域名 `s.coze.cn` 下是完好的（同页另外 11 张图用的都是它）。
> 建这条通道时撞上一个真实的张力：**要修正文** ↔ **硬约束「正文零改动」**。

### 21.1 先把约束的目标说准

「正文零改动」的**真实目标是"不偷偷改内容"**，不是"正文里天塌了也不许碰"。
把两者混为一谈，就会得到两个都不好的选项：要么装瞎（图一直裂），要么破例（约束失去意义）。

⇒ 第三条路：**申报式修复**。要改正文可以，但必须**逐条申报**，由门禁核对
「说过的改了没有、没说过的动了没有」。约束因此**精确化**为：

| 旧表述 | 新表述 |
|---|---|
| 正文零改动 | 正文零**未申报**改动 |

这不是放松 —— 表述更准了，而且**多了一道可核对的手续**（申报条目本身要被审计）。

### 21.2 注册表（唯一申报入口）

真相源 = `references/body-fixes.json`。八项字段，缺一即拦（`BF3` / `validate()`）：

| 字段 | 要求 |
|---|---|
| `id` | 流水号 `BF-00x`，台账与报告按它点名 |
| `slug` | **只对这一个国家生效**（精确匹配，不写通配 —— 防"一条修复摊到全站"） |
| `find` | 基线里**逐字**存在、目标位置唯一的串 |
| `replace` | 改成的串 |
| `why` | 一句话说清"为什么必须改"（**客户视角看得见的问题**） |
| `evidence` | 怎么验证的：命令 + 真实回显（HTTP 码 / content-type / 尺寸 / 肉眼确认）。⚠️ **只写"已确认"不算证据** |
| `owner` | 谁担的 |
| `found_at` | 发现日期 |

### 21.3 三条纪律（都是踩坑得来的）

1. **修复不是第二条写入路径。** 产物链仍是「基线 → 申报修复 → 注入物」，只此一条 ——
   `build()` 里它只是**第 0 步**（比注入更早），并且会在 build 报告里**逐条点名**，
   评审的人必须一眼看到"这次除了标注还动了正文哪里"。
2. **比对时只对基准侧套修复、产物侧不套。**（`baseline_body()` vs `candidate_body()`）
   两侧都套的话，「申报了却没落地」会被判**相等** ⇒ 那是**假通过**，比漏拦更糟。
   这条性质由负向测试 **G1b** 钉死；`N18` 再用真实产物证明一次。
3. **条目过期要删。** 基线更新后缺陷若已被别人修掉，`find` 不再命中 ⇒ `BF2` 按"过期申报"告警。

### 21.6 顺手修掉的一个"假放行"（同类缺陷）

`verify_secondary` 的 S15 查图床可达性是**读 `_img_check.json` 缓存**的。
原实现里「缓存里没有这张图」直接 `continue` —— 等于**"没查过就当好的"**。

**未知就是未知，不许说成已知** —— 与 §19 的「200 不等于可读」同一条纪律。
